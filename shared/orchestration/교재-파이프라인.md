# 교재 집필 파이프라인

> **레이어: 오케스트레이션** — 누가 · 언제 · 누구와 · 무엇을 하는가.
> 이 파일이 담지 않는 것: 각 역할의 판단 기준(→ `~/.claude/agents/*.md`), 작업을 수행하는 절차(→ `shared/skills/*/SKILL.md`), 문체·형광펜 같은 집필 규약(→ `~/.claude/instructions/교재-공통규약.md`).

목차 한 벌을 받아 **책처럼 이어 읽히는 학습용 Markdown 교재**를 만드는 팀의 악보다. 지휘자는 이 파일을 읽고 그대로 배치한다.

---

## 지휘자

지휘자는 **메인 세션**이다. 별도 서브에이전트를 지휘자로 띄우지 않는다 — 위임이 2단으로 겹치면 상태 추적과 게이트 판정이 양쪽으로 흩어진다.

지휘자가 하는 일은 다섯 가지뿐이다.

1. 입력 확정 (Phase 0)
2. 배치 — 어떤 에이전트에게 어떤 입력을 주고 몇 명을 동시에 돌릴지 결정
3. 게이트 판정 — 다음 Phase로 넘길지, 되돌릴지, 사용자에게 물을지
4. 상태 갱신 — `.교재상태.json`
5. 보고 — 사용자에게 진행 상황과 최종 결과

**지휘자가 하지 않는 일: 본문을 쓰는 것. 한 문단도 직접 쓰지 않는다.** 챕터 파일·설계서·검수 리포트를 직접 편집하지 않는다. 오타 하나라도 마찬가지다.

> 수정이 필요하면 담당자에게 근거와 파일 경로를 돌려준다. 계약 변경은 설계자에게, 본문 수정은 집필자에게 배정한다. 지휘자가 대신 고치지 않는다.

**상태 파일(`.교재상태.json`), 사용자 입력의 원문 보존, 작업 공간 생성, 검증·합본 명령 실행**은 지휘자가 직접 한다. 학습 내용의 작성·수정은 작업자가 맡는다. 사용자 입력은 `목차-원문.md`로 보존하고, 번호가 없는 항목에는 표현과 순서를 유지한 채 번호만 붙여 `목차.md`를 만든다.

설치 경로의 `~/.claude`는 기본값이다. `CLAUDE_CONFIG_DIR`를 쓰는 환경에서는 실제 설정 디렉터리로 치환해 절대 경로를 배정한다. 에이전트의 `skills` 필드로 절차를 미리 로드하며, 역할과 절차는 다른 파일로 유지한다.

### 위임할 수 없는 환경이라면

서브에이전트를 띄울 수 없는 세션이라면 — 에이전트 도구가 없거나 역할이 로드되지 않았다면 — **집필을 시작하지 않는다.** 무엇이 필요한지 사용자에게 알리고 멈춘다.

**지휘자가 역할을 번갈아 연기해 책을 완성하고 완료로 보고하지 않는다.** 「리더가 직접 처리한다」는 대개 이 경로로 들어온다. 위임이 막혔을 때 한 명이 다 하는 것은 팀이 아니라 혼자 쓴 책이고, 무엇보다 **쓴 사람이 검수한 책**이 된다.

## 팀 구성

| 에이전트 | 한 줄 역할 | 절차(스킬) | 쓰기 권한 |
|---|---|---|---|
| `curriculum-architect` | 목차를 학습 경로와 챕터 계약으로 바꾼다 | `교재-설계` | `00-설계/` |
| `chapter-writer` | 계약 1장을 본문 1장으로 쓴다 | `챕터-집필` | 자기 챕터 파일 1개 |
| `technical-reviewer` | 사실·코드·계약 위반을 잡는다 | `챕터-검수` (정확성 모드) | `검수/` |
| `learner-advocate` | 독자가 막히는 지점을 잡는다 | `챕터-검수` (독자 모드) | `검수/` |
| `learning-editor` | 낱장을 한 권으로 엮는다 | `교재-엮기` | 전 챕터(연결·표기만) + `index.md` |

**한 에이전트가 두 역할을 겸하지 않는다.** 특히 쓴 사람이 검수하지 않는다 — 자기 글의 빈 구멍은 쓴 사람 눈에만 안 보인다. 정확성과 독자 관점을 한 명에게 몰지 않는다 — 두 축은 서로 다른 것을 놓치고, 한 리포트에 섞이면 심각도 판정이 뭉개진다.

## 작업 공간

```text
<출력경로>/
  index.md                     ← Phase 4 산출. 책의 얼굴
  00-설계/
    설계서.md                  ← 학습 경로 · 의존성 그래프 · 용어집 · 관통 사례
    챕터계약/01.md ~ NN.md     ← 집필자에게 주는 유일한 지시서
  chapters/
    01-<슬러그>.md
  검수/
    01-정확성.md  01-독자.md
  .교재상태.json               ← 지휘자 전용. 재개의 근거
```

경로 규칙과 파일 스키마는 `shared/orchestration/산출물-계약.md`.

## Phase

| # | 이름 | 담당 | 동시 실행 | 통과 조건(게이트) |
|---|---|---|---|---|
| 0 | 접수 | 지휘자 | — | 입력 4종 확정 |
| 1 | 설계 | `curriculum-architect` ×1 | — | plan 검사 통과 + 필요한 범위 변경 확인 |
| 2 | 집필 | `chapter-writer` ×N | 최대 3 | 챕터별 자가 점검 통과 |
| 3 | 검수 | `technical-reviewer` + `learner-advocate` | 전체 작업자 최대 3명 | 현재 판본의 두 검수 + S1 0건 |
| 4 | 엮기 | `learning-editor` ×1, 이후 독립 검수자 | 편집과 해당 원고 검수는 겹치지 않음 | 편집된 원고 재검수 + final 검사 통과 |
| 5 | 인계 | 지휘자 | — | 검증 결과와 남은 항목 보고 |

### 요청 모드의 라우팅

`교재` 스킬은 의도를 접수한다. 실제 진입과 종료 단계는 이 문서에서만 정한다.

- 신규: Phase 0부터. 기존 파일이 있으면 먼저 확인한다
- 이어서: 상태와 실제 산출물·해시를 대조해 최초 미완료 작업부터 재개한다. 상태 파일이 없으면 기존 산출물을 검사해 복구하며 신규로 덮어쓰지 않는다
- 검수: Phase 3을 수행하고 판정만 보고한다. 추가 집필·편집 요청이 없으면 원고를 바꾸지 않는다
- 재집필: 지정 챕터를 Phase 2로 돌리고 영향받은 후행 챕터를 확인한 뒤 검수·편집·최종 검증까지 수행한다
- 상태: 읽기 전용으로 조회하고 종료한다. 상태 파일도 갱신하지 않는다
- 설계: Phase 1 산출물을 전달하고 종료한다

### Phase 0 — 접수

지휘자 단독. 다음 4종을 확정한다. 빠진 것만 묻는다.

1. **목차** — 원문 텍스트나 파일 경로. 사진·PDF면 경로
2. **독자** — 없으면 `~/.claude/instructions/교재-공통규약.md`의 기본 독자로 두고 **가정을 밝힌다**
3. **출력 경로** — 없으면 `./<책이름>/`을 제안
4. **깊이** — `표준`(챕터당 25~40분) / `압축`(15분) / `정밀`(45~60분). 없으면 `표준`

작업 공간을 만들고 `.교재상태.json`을 초기화한다. 여기까지는 위임하지 않는다 — 위임 비용이 작업보다 크다.

### Phase 1 — 설계

`curriculum-architect` 1명. 챕터가 몇 개든 설계는 한 명이 한다. **책 전체를 한 머리가 봐야 의존성과 중복이 보인다.**

넘기는 것: 목차 원문 · 독자 · 깊이 · 출력 경로 · 공통규약 경로.

받는 것: `00-설계/설계서.md`, `00-설계/챕터계약/NN.md` 전부.

**게이트 — 설계 검증.** `book.py check <출력경로> --stage plan`을 통과한 뒤 지휘자는 다음을 사용자에게 보인다.

- 챕터 목록 (번호 · 제목 · 예상 시간)
- 원래 목차에서 **바꾼 것**: 합침 · 나눔 · 순서 변경 · 추가한 연결 챕터 — 각각 한 줄 이유와 함께
- 관통 사례 하나
- 총 예상 분량

목차 삭제·범위 확대·학습 순서 변경 등 이미 승인받지 않은 중요한 변경만 확인한다. 요청 범위 안의 구체화나 이미 허용한 재구성은 설명 후 계속한다. `설계만` 요청이면 여기서 종료한다.

### Phase 2 — 집필

`chapter-writer` N명. **의존성 레벨 단위로 배치한다.**

- 설계서의 의존성 그래프에서 선수 챕터가 모두 현재 판본으로 Phase 3을 통과한 챕터만 배치 대상
- 같은 레벨은 **최대 3개 동시**. 3을 넘기지 않는 이유는 속도가 아니라 일관성이다 — 동시에 도는 집필자가 늘수록 같은 용어를 다르게 쓸 확률이 올라가고, 엮기 단계의 수정량이 그보다 빨리 는다
- 한 레벨의 집필이 끝나면 Phase 3에서 그 레벨을 검수하고, 통과 후 다음 레벨로 간다. 전체 집필 후 한꺼번에 검수하지 않는다

각 집필자에게 넘기는 것 — **경로만 넘기고 내용을 인라인하지 않는다.**

```text
챕터 계약:   <출력경로>/00-설계/챕터계약/NN.md
공통규약:    ~/.claude/instructions/교재-공통규약.md
용어집·사례: <출력경로>/00-설계/설계서.md 의 「용어집」·「관통 사례」 절만
선행 요약:   <선행 챕터 파일>의 frontmatter `요약` 필드 (있을 때만)
쓸 파일:     <출력경로>/chapters/NN-<슬러그>.md
```

**넘기지 않는 것: 다른 챕터의 본문.** 앞 챕터 전문을 주면 집필자는 그걸 요약하며 시작하고, 같은 설명이 두 챕터에 중복된다. 연결은 계약의 「이어받을 문장」과 선행 챕터 요약 한 줄이면 충분하다.

### Phase 3 — 검수

챕터 하나당 `technical-reviewer` 1명 + `learner-advocate` 1명을 배정한다. 여유가 있으면 동시에 실행하되 **모든 역할을 합쳐 작업자 최대 3명**이다. 슬롯이 부족하면 순차 실행해도 두 검수의 독립성은 유지한다.

**두 검수자는 서로의 리포트를 보지 않는다.** 각 축에서 근거가 있는 지적이면 한 명만 발견했어도 유효하다. 재검수자는 자기 축의 이전 리포트만 읽고 ID를 이어받는다.

넘기는 것: 챕터 파일 · 해당 계약 · 설계서 · 선수 챕터 경로 · 공통규약 · 쓸 리포트 경로. 원자료가 있으면 함께 전달한다. 독자 검수자는 선수 챕터에서 실제로 설명한 범위를 확인할 수 있다.

**검수자는 시작 전에 대상 원고의 해시를 기록한다.** 그 해시가 판정의 유효기간이다(→ 산출물 계약 「3. 검수 리포트」).

**검수 중인 챕터에는 집필자를 배치하지 않는다.** 검수자는 멈춰 있는 판본을 본다. 읽는 도중에 내용이 바뀌면 그 판정은 어느 판본에 대한 것도 아니게 된다.

**게이트 — S1 0건.**

- S1(치명) 있음 → Phase 2로 **해당 챕터만** 되돌린다. 상한은 챕터가 아니라 **지적 ID** 기준이다 — 같은 ID가 2회 살아남으면 거기서 멈춘다. 재집필마다 다른 S1이 나오는 챕터는 수렴하는 중이므로 계속 간다. 다만 한 챕터의 총 재집필이 4회를 넘으면 **집필 문제가 아니라 계약 문제**로 보고 Phase 1로 올려 계약을 고친다
- S2만 있음 → 다음 재집필 기회에 동봉하되 S2만으로 되돌리지 않는다. 편집과 인계는 허용하며 미처리 ID·이유를 `index.md`의 「남은 것」과 최종 보고에 공개한다. 핵심 사실이 미확인인 상태는 완료로 표시하지 않는다
- S3만 있음 → Phase 4의 `learning-editor`에게 넘긴다

되돌릴 때 새 `chapter-writer`에게 주는 것: 기존 챕터 파일 + 두 리포트 + 계약. **리포트를 요약해서 전달하지 않는다** — 요약하는 순간 지휘자가 품질 판단에 개입하게 된다.

#### 판정이 무효가 되는 때

통과 판정은 **특정 판본에 대한 것**이지 챕터에 대한 것이 아니다. 다음 경우 그 챕터의 판정은 무효이고, 상태는 `stale`이 된다.

| 무엇이 바뀌면 | 무효가 되는 범위 |
|---|---|
| 원고가 바뀌었다 (재집필) | 그 챕터의 두 판정 모두. 재검수 없이 확정하지 않는다 |
| 선수 챕터 본문이 바뀌었다 | 그 본문을 읽은 후행 검수의 검수입력해시가 달라지므로 재검수. 요약까지 달라졌다면 후행 집필 입력도 확인 |
| 계약 또는 공통 설계가 바뀌었다 | 입력해시가 다른 원고와 두 판정. 담당 집필자가 영향 확인 후 필요한 수정과 입력해시 갱신, 이후 재검수 |
| 선행 챕터의 `요약`이 바뀌었다 | 그 요약을 사용한 후행 챕터를 stale로 두고 전제·사례·설명까지 확인. 후행 요약도 달라지면 의존성 그래프를 따라 전파 |

`입력해시`는 계약·설계서·선수 요약을 묶는다. 변경 영향을 확인하기 전에 해시만 갱신하지 않는다. 선수가 stale/blocked이면 그 후행 작업도 보류한다. 공통 설계서는 파일 전체를 해시하므로 표기만 바꿔도 영향 확인이 필요하다.

기계로 확인할 수 있다. Phase를 넘기기 전에 돌린다.

```bash
python3 ~/.claude/orchestration/book.py check <출력경로> --stage draft --chapter 03
python3 ~/.claude/orchestration/book.py check <출력경로> --stage review --chapter 03
```

#### 막혔을 때

같은 지적 ID가 2회 살아남고 계약을 고쳐도 풀리지 않으면 — 대개 사용자만 답할 수 있는 사실 공백이다 — 그 챕터를 `blocked`로 기록하고 **무엇이 필요한지 사용자에게 알린다.** 나머지 챕터는 계속 간다. 기준을 낮춰 통과시키거나 추측으로 메우지 않는다.

재시도 횟수는 **지적 ID별로**, 작업자가 바뀌어도 이어서 센다. 새 서브에이전트에게 배정했다고 0으로 돌아가면 무한 재시도가 된다.

### Phase 4 — 엮기

`learning-editor` 1명. 전 챕터의 현재 판본이 검수를 통과한 뒤에만 시작한다. 최종 확정은 편집과 재검수가 끝난 뒤다.

시작 전에 지휘자가 확인한다. **오류가 하나라도 있으면 엮기를 배정하지 않는다** — 낡은 판정 위에서 엮으면 검수받지 않은 문장이 책에 들어간다.

```bash
python3 ~/.claude/orchestration/book.py check <출력경로> --stage review
```

넘기는 것: 출력 경로 전체 · 설계서 · 모든 검수 리포트의 S3 항목.

에디터가 **하지 않는 것**: 새 내용 추가, 사실 판단. 설명이 틀렸다고 판단되면 고치지 말고 「지휘자 보고」 절에 적는다.

편집이 끝나면 다음 순서를 따른다.

1. 편집자의 변경 파일·보고를 받고 `--stage draft`로 구조와 링크를 확인한다
2. 편집된 챕터와 선수 본문 변경으로 검수입력해시가 달라진 후행 챕터를 두 독립 검수자에게 다시 배정한다. 검수자가 새 판본을 읽은 뒤 해시를 기록한다
3. 설계 누락·사실 의심은 해당 설계자·집필자·검수자에게 돌린다. 내용 수정은 다시 검수하고, 연결에 영향이 있으면 편집자에게 재배정한다
4. `index.md`의 미처리 항목을 최신 판정에 맞게 편집자가 갱신한다. `--stage final` 통과 후 상태 파일에서 확정한다

원고의 frontmatter를 `확정`으로 고쳐 상태를 표시하지 않는다. 메타데이터 변경도 원고 해시를 바꾸므로 작업 상태는 `.교재상태.json`에서만 관리한다.

### Phase 5 — 인계

`book.py check <출력경로> --stage final`을 통과한 뒤 지휘자가 보고한다. 오류가 남으면 완료 대신 진행 상황과 막힌 항목을 보고한다.

- 만든 것: 챕터 수 · 총 분량 · 예상 학습 시간 · `index.md` 경로
- 원래 목차에서 바꾼 것
- 남은 것: 미해결 S2/S3, 에디터가 올린 사실 의심 항목, 집필자들의 「이월 제안」
- 다음에 할 수 있는 것 (예: `/교재 검수`, 특정 챕터 재집필)

단일 파일로 읽고 싶다는 요청이 있으면 합본을 만든다. **합본은 재생성물이다** — 직접 고치지 않는다. 고칠 것이 있으면 챕터를 고치고 다시 만든다.

```bash
python3 ~/.claude/orchestration/book.py build <출력경로>
```

## 되돌림 · 재개

**되돌림**은 Phase 3·4 → 2(본문), → 1(계약), → 3(편집 후 재검수)이다. 편집 이후 발견된 결함도 해결·재검수하기 전에는 확정하지 않는다.

**재개**는 `.교재상태.json`을 읽고 실제 파일·입력해시·검수해시를 대조한다. 상태는 작업 이력이고 검증 통과를 대신하지 않는다. 어긋나면 최신 파일을 검사해 stale/미완료로 복구한다. 파일이 있다는 이유만으로 통과 처리하지 않는다.

## 배치 원칙

- **배정은 「배정 메시지」 형식으로 한다** (→ 산출물 계약 「6. 배정 메시지」). 절차를 메시지에 복사하지 말고 스킬 경로만 준다. 입력은 경로로 주고 내용을 붙여넣지 않는다
- **두 작업자가 같은 파일을 동시에 소유하지 않는다.** 배정 메시지의 `쓸 수 있는 파일`이 소유권이고, 그 밖은 읽기 전용이다
- **집필자·검수자 한 작업에는 한 챕터.** 설계자와 편집자는 책 전체를 맡는다
- **읽기 전용 역할에는 쓰기 경로를 하나만 준다.** 검수자는 `검수/` 밖에 쓰지 않는다
- 내용상 같은 실패가 반복되면 계약 또는 작업 범위를 재검토한다. 일시적인 도구 오류는 원고나 계약을 바꾸지 않고 제한적으로 재시도한다
- 서브에이전트 결과는 사용자에게 자동으로 보이지 않는다. 지휘자가 **옮겨 적는다**
