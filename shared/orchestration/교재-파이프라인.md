# 교재 집필 파이프라인

> **레이어: 오케스트레이션** — 누가 · 언제 · 누구와 · 무엇을 하는가.
> 이 파일이 담지 않는 것: 각 역할의 판단 기준(→ `~/.claude/agents/*.md`), 작업을 수행하는 절차(→ `shared/skills/*/SKILL.md`), 문체·형광펜 같은 집필 규약(→ `~/.claude/instructions/교재-공통규약.md`).

목차 한 벌을 받아 **책처럼 이어 읽히는 학습용 Markdown 교재**를 만드는 팀의 악보다. 지휘자는 이 파일을 읽고 그대로 배치한다.

---

## 지휘자

지휘자는 **메인 세션**이다. 별도 서브에이전트를 지휘자로 띄우지 않는다 — 위임이 2단으로 겹치면 상태 추적과 게이트 판정이 양쪽으로 흩어진다.

지휘자가 하는 일은 다섯 가지뿐이다.

1. 입력 확정 (Phase 0)
2. 배치 — 어떤 에이전트에게 어떤 입력을 주고 몇 명을 동시에 돌릴지 결정
3. 게이트 판정 — 다음 Phase로 넘길지, 되돌릴지, 사용자에게 물을지
4. 상태 갱신 — `.교재상태.json`
5. 보고 — 사용자에게 진행 상황과 최종 결과

**지휘자가 하지 않는 일: 본문을 쓰는 것. 한 문단도 직접 쓰지 않는다.** 챕터 파일·설계서·검수 리포트를 직접 편집하지 않는다. 오타 하나라도 마찬가지다.

> 수정이 필요하면 담당자에게 근거와 파일 경로를 돌려준다. 계약 변경은 설계자에게, 본문 수정은 집필자에게 배정한다. 지휘자가 대신 고치지 않는다.

**상태 파일(`.교재상태.json`), 사용자 입력의 원문 보존, 작업 공간 생성, 검증·합본 명령 실행**은 지휘자가 직접 한다. 학습 내용의 작성·수정은 작업자가 맡는다. 사용자 입력은 `목차-원문.md`로 보존하고, 번호가 없는 항목에는 표현과 순서를 유지한 채 번호만 붙여 `목차.md`를 만든다.

설치 경로의 `~/.claude`는 기본값이다. `CLAUDE_CONFIG_DIR`를 쓰는 환경에서는 실제 설정 디렉터리로 치환해 절대 경로를 배정한다. 에이전트의 `skills` 필드로 절차를 미리 로드하며, 역할과 절차는 다른 파일로 유지한다.

### 위임할 수 없는 환경이라면

서브에이전트를 띄울 수 없는 세션이라면 — 에이전트 도구가 없거나 역할이 로드되지 않았다면 — **집필을 시작하지 않는다.** 무엇이 필요한지 사용자에게 알리고 멈춘다.

**지휘자가 역할을 번갈아 연기해 책을 완성하고 완료로 보고하지 않는다.** 「리더가 직접 처리한다」는 대개 이 경로로 들어온다. 위임이 막혔을 때 한 명이 다 하는 것은 팀이 아니라 혼자 쓴 책이고, 무엇보다 **쓴 사람이 검수한 책**이 된다.

## 팀 구성

| 에이전트 | 한 줄 역할 | 절차(스킬) | 쓰기 권한 |
|---|---|---|---|
| `curriculum-architect` | 목차를 학습 경로와 챕터 계약으로 바꾼다 | `교재-설계` | `00-설계/` |
| `chapter-writer` | 계약 1장을 본문 1장으로 쓴다 | `챕터-집필` | 자기 챕터 파일 1개 |
| `technical-reviewer` | 사실·코드·계약 위반을 잡는다. 집필 전에는 설계를 같은 축으로 본다 | `챕터-검수` (정확성 축) | `검수/` |
| `learner-advocate` | 독자가 막히는 지점을 잡는다. 집필 전에는 설계를 같은 축으로 본다 | `챕터-검수` (독자 축) | `검수/` |
| `learning-editor` | 낱장을 한 권으로 엮는다 | `교재-엮기` | 전 챕터(연결·표기만) + `index.md` |

**한 에이전트가 두 역할을 겸하지 않는다.** 특히 쓴 사람이 검수하지 않는다 — 자기 글의 빈 구멍은 쓴 사람 눈에만 안 보인다. 정확성과 독자 관점을 한 명에게 몰지 않는다 — 두 축은 서로 다른 것을 놓치고, 한 리포트에 섞이면 심각도 판정이 뭉개진다.

## 작업 공간

```text
<출력경로>/
  index.md                     ← Phase 4 산출. 책의 얼굴
  00-설계/
    설계서.md                  ← 학습 경로 · 의존성 그래프 · 용어집 · 관통 사례
    챕터계약/01.md ~ NN.md     ← 집필자에게 주는 유일한 지시서
  chapters/
    01-<슬러그>.md
  검수/
    설계-정확성.md  설계-독자.md   ← Phase 1의 설계 검수
    01-정확성.md  01-독자.md
  .교재상태.json               ← 지휘자 전용. 재개의 근거이자 캐시
  미확인-수락.md               ← 지휘자 전용. 사용자의 미확인 수락 기록(추가 전용)
  .교재기록.jsonl              ← 훅 전용. 누가 어디에 썼는지(감사용, 판정 근거 아님)
```

경로 규칙과 파일 스키마는 `shared/orchestration/산출물-계약.md`.

## Phase

| # | 이름 | 담당 | 동시 실행 | 통과 조건(게이트) |
|---|---|---|---|---|
| 0 | 접수 | 지휘자 | — | 입력 4종 확정 + intake 검사 통과 |
| 1 | 설계 | `curriculum-architect` ×1, 이후 두 검수자(설계) | 두 설계 검수는 동시 | plan 검사 → 설계 검수 S1 0건(design 검사) + 필요한 범위 변경 확인 |
| 2 | 집필 | `chapter-writer` ×N | 최대 3 | 챕터별 자가 점검 통과 |
| 3 | 검수 | `technical-reviewer` + `learner-advocate` | 전체 작업자 최대 3명 | 현재 판본의 두 검수 + S1 0건 |
| 4 | 엮기 | `learning-editor` ×1, 이후 독립 검수자 | 편집과 해당 원고 검수는 겹치지 않음 | 편집된 원고 재검수 + final 검사 통과 |
| 5 | 인계 | 지휘자 | — | 검증 결과와 남은 항목 보고 |

### 요청 모드의 라우팅

`교재` 스킬은 의도를 접수한다. 실제 진입과 종료 단계는 이 문서에서만 정한다.

- 신규: Phase 0부터. 기존 파일이 있으면 먼저 확인한다
- 이어서: 상태와 실제 산출물·해시를 대조해 최초 미완료 작업부터 재개한다. 상태 파일이 없으면 기존 산출물을 검사해 복구하며 신규로 덮어쓰지 않는다
- 검수: Phase 3을 수행하고 판정만 보고한다. 추가 집필·편집 요청이 없으면 원고를 바꾸지 않는다
- 재집필: 지정 챕터를 Phase 2로 돌리고 영향받은 후행 챕터를 확인한 뒤 검수·편집·최종 검증까지 수행한다
- 상태: 읽기 전용으로 조회하고 종료한다. 상태 파일도 갱신하지 않는다
- 설계: 설계 검수까지 포함한 Phase 1 산출물을 전달하고 종료한다

### Phase 0 — 접수

지휘자 단독. 다음 4종을 확정한다. 빠진 것만 묻는다.

1. **목차** — 원문 텍스트나 파일 경로. 사진·PDF면 경로
2. **독자** — 없으면 `~/.claude/instructions/교재-공통규약.md`의 기본 독자로 두고 **가정을 밝힌다**
3. **출력 경로** — 없으면 `./<책이름>/`을 제안
4. **깊이** — `표준` / `압축` / `정밀`. 없으면 `표준`. 깊이별 읽기 시간과 분량은 `~/.claude/skills/교재-설계/SKILL.md` 4단계 표가 정한다

작업 공간을 만들고 `목차-원문.md`·`목차.md`를 쓰고 `.교재상태.json`을 초기화한다. 여기까지는 위임하지 않는다 — 위임 비용이 작업보다 크다.

**게이트 — 접수 검증.** 설계자를 배정하기 전에 돌린다. 오류가 있으면 지휘자가 고친다 — 이 단계의 파일은 모두 지휘자 소유다.

```bash
python3 ~/.claude/orchestration/book.py check <출력경로> --stage intake
```

### Phase 1 — 설계

`curriculum-architect` 1명. 챕터가 몇 개든 설계는 한 명이 한다. **책 전체를 한 머리가 봐야 의존성과 중복이 보인다.**

넘기는 것: 목차 원문 · 독자 · 깊이 · 출력 경로 · 공통규약 경로.

받는 것: `00-설계/설계서.md`, `00-설계/챕터계약/NN.md` 전부.

**게이트 — 설계 검증.** 먼저 `book.py check <출력경로> --stage plan`을 통과시킨다. 설계 점검표 중 셀 수 있는 것은 이 검사가 센다. 실패하면 오류 문구를 설계자에게 돌려준다.

**설계 검수.** plan을 통과하면 `technical-reviewer`와 `learner-advocate`를 동시에 1명씩 배정해 설계 전체를 각자의 축으로 검수하게 한다(산출물 계약 3절 「설계 검수 리포트」, 6절의 설계 검수 배정). 셀 수 없는 설계 결함 — 계약이 지시하는 틀린 사실, 선수지식 역전, 소유 충돌 — 을 원고가 생기기 전에 잡는다. 계약의 결함은 원고 N장에 복제된 뒤에 잡으면 재집필 N번으로 갚는다.

```bash
python3 ~/.claude/orchestration/book.py check <출력경로> --stage design
```

- S1 있음 → 두 설계 리포트 경로를 설계자에게 주고 재설계를 배정한다. 남은 S2·S3도 같은 배정에서 함께 고친다. 고친 뒤 두 축 모두 `계기: 재설계`로 다시 검수한다 — 계약 한 장을 고쳐도 설계 판정 전체가 낡는다. 리포트를 받을 때마다 `book.py tally <출력경로>`의 `설계`를 보고, `막힘`이 차 있으면 「막혔을 때」로 간다
- S1 없이 S2가 있음 → design은 통과했지만 **집필 전에 한 번** 재설계를 배정한다(`tally`의 `설계` → `재설계`가 0일 때만). 두 설계 리포트를 주고 S2·S3를 고치게 한 뒤 두 축이 `계기: 재설계`로 다시 검수한다. 설계 S2는 집필자에게 넘어가지 않는다 — 집필자는 계약만 보므로 계약에 남은 빈틈은 원고 N장에 그대로 복제된다. 원고가 없는 지금 고치면 재설계 한 번이고, 집필 뒤에 고치면 계약버전과 재집필 N번이다
- 그 뒤에도 남은 S2·S3, 또는 S3만 있음 → 막지 않는다. 승인 화면에 남은 ID를 함께 보이고 다음 재설계에 동봉한다
- 「미확인」 → 막지 않는다. 그 사실이 해당 계약의 「근거 확인 필요 항목」에 있는지 설계자에게 확인시킨다

design을 통과한 뒤 지휘자는 다음을 사용자에게 보인다.

- 챕터 목록 (번호 · 제목 · 예상 시간)
- 원래 목차에서 **바꾼 것**: 합침 · 나눔 · 순서 변경 · 추가한 연결 챕터 — 각각 한 줄 이유와 함께
- 관통 사례 하나
- 총 예상 분량

목차 삭제·범위 확대·학습 순서 변경 등 이미 승인받지 않은 중요한 변경만 확인한다. 요청 범위 안의 구체화나 이미 허용한 재구성은 설명 후 계속한다. `설계만` 요청이면 여기서 종료한다.

### Phase 2 — 집필

`chapter-writer` N명. **의존성 레벨 단위로 배치한다.**

- 설계서의 의존성 그래프에서 선수 챕터가 모두 현재 판본으로 Phase 3을 통과한 챕터만 배치 대상
- 같은 레벨은 **최대 3개 동시**. 3을 넘기지 않는 이유는 속도가 아니라 일관성이다 — 동시에 도는 집필자가 늘수록 같은 용어를 다르게 쓸 확률이 올라가고, 엮기 단계의 수정량이 그보다 빨리 는다
- 한 레벨의 집필이 끝나면 Phase 3에서 그 레벨을 검수하고, 통과 후 다음 레벨로 간다. 전체 집필 후 한꺼번에 검수하지 않는다

각 집필자에게 넘기는 것 — **경로만 넘기고 내용을 인라인하지 않는다.**

```text
챕터 계약:   <출력경로>/00-설계/챕터계약/NN.md
공통규약:    ~/.claude/instructions/교재-공통규약.md
용어집·사례: <출력경로>/00-설계/설계서.md 의 「용어집」·「관통 사례」 절만
선행 요약:   <선행 챕터 파일>의 frontmatter `요약` 필드 (있을 때만)
쓸 파일:     <출력경로>/chapters/NN-<슬러그>.md
```

**넘기지 않는 것: 다른 챕터의 본문.** 앞 챕터 전문을 주면 집필자는 그걸 요약하며 시작하고, 같은 설명이 두 챕터에 중복된다. 연결은 계약의 「이어받을 문장」과 선행 챕터 요약 한 줄이면 충분하다.

### Phase 3 — 검수

챕터 하나당 `technical-reviewer` 1명 + `learner-advocate` 1명을 배정한다. 여유가 있으면 동시에 실행하되 **모든 역할을 합쳐 작업자 최대 3명**이다. 슬롯이 부족하면 순차 실행해도 두 검수의 독립성은 유지한다.

**두 검수자는 서로의 리포트를 보지 않는다.** 각 축에서 근거가 있는 지적이면 한 명만 발견했어도 유효하다. 재검수자는 자기 축의 이전 리포트만 읽고 ID를 이어받는다. 게이트를 직접 돌릴 때는 `--axis <자기 축>`을 붙인다 — 다른 축의 지적 개수도 상대 리포트의 일부다.

넘기는 것: 챕터 파일 · 해당 계약 · 설계서 · 공통규약 · 쓸 리포트 경로, 그리고 **독자 검수자에게만** 선수 챕터 경로(산출물 계약 3절 「축별 검수 입력」). 원자료가 있으면 함께 전달한다. 독자 검수자는 선수 챕터에서 실제로 설명한 범위를 확인할 수 있다. 정확성 검수자에게 선수 본문을 주지 않는 것은 그 축의 검수입력해시가 선수 본문을 묶지 않기 때문이다 — 묶지 않은 입력에 기댄 판정은 그 입력이 바뀌어도 낡았다고 잡히지 않는다.

**검수자는 시작 전에 대상 원고의 해시를 기록한다.** 그 해시가 판정의 유효기간이다(→ 산출물 계약 「3. 검수 리포트」).

**검수 중인 챕터에는 집필자를 배치하지 않는다.** 검수자는 멈춰 있는 판본을 본다. 읽는 도중에 내용이 바뀌면 그 판정은 어느 판본에 대한 것도 아니게 된다.

**게이트 — S1 0건.**

- S1(치명) 있음 → 먼저 `book.py tally <출력경로> --chapter NN`을 돌린다. `막힘`이 차 있으면 되돌리지 않고 「막혔을 때」로 간다. 비어 있으면 **귀속**(산출물 계약 3절 「귀속」)으로 되돌릴 곳을 정한다
  - `계약귀속`이 비어 있지 않다 → **Phase 1로.** 두 리포트 경로를 설계자에게 주고 계약 수정을 배정한다(`계약버전` +1). 같은 챕터의 `원고` S1도 그 뒤 재집필에서 함께 고친다. 범위·순서가 바뀌면 사용자에게 확인한다. 설계 검수(`계기: 재설계`)와 design 게이트를 거쳐 Phase 2로 간다. 집필자에게 바로 돌리지 않는다 — 같은 계약으로 다시 쓰면 같은 결함이 나온다
  - 귀속이 모두 `원고` → Phase 2로 **해당 챕터만** 되돌린다. 재집필마다 다른 S1이 나오는 챕터는 수렴하는 중이므로 상한 안에서는 계속 간다
- S2만 있음 → 다음 재집필 기회에 동봉하되 S2만으로 되돌리지 않는다. 편집과 인계는 허용하며 미처리 추적 키·이유를 `index.md`의 「남은 것」과 최종 보고에 공개한다(산출물 계약 3절 「남은 지적 공개」 — final 게이트가 대조한다)
- S3만 있음 → Phase 4의 `learning-editor`에게 넘긴다
- 귀속이 `계약`인 S2·S3 → 집필자도 편집자도 고칠 수 없다. 아래 「계약 귀속 S2·S3」로 모아 둔다
- 「미확인」이 있음 → 판정과 별개로 진행은 막지 않는다. 다만 final 게이트가 막으므로 Phase 4를 시작하기 전에 사용자에게 한 번에 묶어 묻는다(→ Phase 5 「미확인을 물을 때」)

리포트를 받을 때마다 `tally`를 돌려 상태 파일의 `재집필`·`편집`·`열린지적`을 덮어쓴다. **지휘자가 기억으로 세지 않는다.** 대화가 끊기거나 세션이 바뀌어도 횟수가 이력에서 그대로 나오게 하기 위해서다.

되돌릴 때 새 `chapter-writer`에게 주는 것: 기존 챕터 파일 + 두 리포트 + 계약. **리포트를 요약해서 전달하지 않는다** — 요약하는 순간 지휘자가 품질 판단에 개입하게 된다. 재집필하는 집필자는 정확성 리포트가 답한 `확인 필요` 표시를 지운다(산출물 계약 3절 「확인 필요 표시」).

#### 계약 귀속 S2·S3

계약이 원인인 S2·S3는 계약을 고쳐야 없어지지만, **그것만으로 계약버전을 올리지 않는다.** 계약을 고치면 그 챕터의 재집필과 두 축 재검수가 따라오고, S2·S3는 그 값을 치를 만큼 막지 않는다. 대신 계약을 어차피 고칠 때 한꺼번에 넘긴다.

- 모으기: 리포트를 받을 때마다 돌리는 `tally`의 `계약대기`가 목록이다. 설계 검수 리포트의 열린 S2·S3는 `--chapter` 없이 돌린 `tally`의 `설계` → `계약대기`에 나온다. 지휘자가 따로 적어 두지 않는다
- 넘기는 때: 그 챕터의 계약을 고치는 배정이 생길 때 — 계약 귀속 S1, 「막혔을 때」의 계약 수정, 사용자의 범위 변경. 설계자에게 해당 리포트 경로와 `계약대기`의 추적 키를 함께 준다. 리포트를 요약하지 않는다
- 끝까지 그런 배정이 없으면: 인계에서 미해결 S2·S3로 공개한다. `index.md` 「남은 것」에 추적 키와 `(계약 귀속)`을 적어 두면 다음 개정 때 설계자가 찾는다
- 그 줄에 `확인 필요` 표시가 있어도 기다리지 않는다. 표시는 리포트가 답했으면 지운다 — 결함은 지적 ID가 따로 추적한다

#### 판정이 무효가 되는 때

통과 판정은 **특정 판본에 대한 것**이지 챕터에 대한 것이 아니다. 다음 경우 그 챕터의 판정은 무효이고, 상태는 `stale`이 된다.

| 무엇이 바뀌면 | 무효가 되는 범위 |
|---|---|
| 원고가 바뀌었다 (재집필) | 그 챕터의 두 판정 모두. 재검수 없이 확정하지 않는다 |
| 선수 챕터 본문이 바뀌었다 | 그 본문을 읽은 후행 검수의 검수입력해시가 달라지므로 재검수. 요약까지 달라졌다면 후행 집필 입력도 확인 |
| 계약 또는 공통 설계가 바뀌었다 | 두 설계 판정(설계 재검수, `계기: 재설계`), 입력해시가 다른 원고와 두 판정. 설계 검수가 design을 통과한 뒤 담당 집필자가 영향 확인 후 필요한 수정과 입력해시 갱신, 이후 재검수 |
| 선행 챕터의 `요약`이 바뀌었다 | 그 요약을 사용한 후행 챕터를 stale로 두고 전제·사례·설명까지 확인. 후행 요약도 달라지면 의존성 그래프를 따라 전파 |

`입력해시`는 계약·설계서·선수 요약을 묶는다. 변경 영향을 확인하기 전에 해시만 갱신하지 않는다. 선수가 stale/blocked이면 그 후행 작업도 보류한다. 공통 설계서는 파일 전체를 해시하므로 표기만 바꿔도 영향 확인이 필요하다.

기계로 확인할 수 있다. Phase를 넘기기 전에 돌린다.

```bash
python3 ~/.claude/orchestration/book.py check <출력경로> --stage draft --chapter 03
python3 ~/.claude/orchestration/book.py check <출력경로> --stage review --chapter 03
```

#### 막혔을 때

상한은 두 개이고, 어느 쪽이든 걸리면 같은 길로 간다. 세는 법은 산출물 계약 3절 「상한 집계」, 세는 도구는 `book.py tally`다.

| 상한 | 값 | 왜 이 숫자인가 |
|---|---|---|
| 같은 지적이 살아남은 횟수 | **2회** | 집필자는 그 지적이 적힌 리포트를 받고 두 번 고쳤다. 두 번 다 같은 결함이 남았다면 원인은 솜씨가 아니라 입력 — 계약에 없는 사실, 서로 부딪히는 요구 — 일 가능성이 높고, 같은 입력으로 세 번째를 써도 같은 결과가 나온다 |
| 한 챕터의 재집필 횟수 | **4회** | 재집필마다 두 축이 다시 검수하므로 4회면 검수가 첫 회 포함 10번 돈다. 매번 다른 S1이 나와도 그쯤이면 계약이 한 챕터에 너무 많이 담았거나 소유 범위가 흐린 것이다 |

`tally`의 `막힘`이 차 있으면:

1. 그 챕터를 `blocked`로 두고 `막힘`에 `tally`의 문장과 **필요한 것**을 적는다. 그 챕터를 선수로 둔 후행 작업도 보류한다. 나머지 챕터는 계속 간다
2. 사용자에게 알린다 — 걸린 상한, 해당 리포트 경로와 지적 ID, 지휘자가 보기에 필요한 것(사용자만 아는 사실, 계약 범위 조정, 챕터 제외). 리포트 내용은 요약하지 않고 경로와 ID로 가리킨다
3. 사용자의 답이 오면 `curriculum-architect`에게 계약 수정을 배정하고 `계약버전`을 올린다. 사실을 받았으면 계약에 넣고, 범위를 줄이기로 했으면 계약에서 뺀다. **상한은 계약버전마다 새로 센다** — 같은 계약으로 다시 돌리는 길은 없다
4. 새 계약으로 설계 검수(`계기: 재설계`)와 design 게이트를 거쳐 Phase 2부터 다시 간다

설계 검수의 같은 지적이 재설계 2회를 살아남았을 때(`tally`의 `설계` → `막힘`)도 같은 길이다. 다만 멈추는 것은 책 전체다 — 계약이 정해지지 않으면 어느 챕터도 집필을 시작하지 않는다. 설계 지적의 횟수는 계약버전이 아니라 지적 ID에 묶이므로, 사용자의 답으로 고친 설계가 그 ID를 해결해야 풀린다.

하지 않는 것: 상한을 올리는 것, 같은 계약으로 한 번 더 돌리는 것, 지휘자나 사용자가 S1을 낮추거나 남긴 채 통과시키는 것(**강제 PASS는 없다**), 추측으로 메우는 것. 사용자가 「그냥 넘어가자」고 하면 그 챕터를 빼거나 계약을 줄이는 선택지를 보인다.

#### 도구 오류

작업자가 완료 보고 없이 끝났다, 도구 호출이 일시 오류로 실패했다, 시간이 초과됐다 — 내용이 아니라 실행의 실패다. 보고가 있는데 형식만 다르면 여기에 들지 않는다. 파일과 게이트로 확인한다(산출물 계약 6절 「완료 보고」). **같은 배정을 같은 작업 ID로 2회까지 다시 보낸다.** 회차(`-rN`)를 올리지 않고, 원고·계약·리포트를 바꾸지 않는다. 다시 보내기 전에 기대 해시를 새로 계산한다.

세 번째 실패면 일시 오류가 아니다. 그 챕터를 `blocked`로 두고 `막힘`에 작업 ID·오류 문구를 적어 사용자에게 알린다. 이 횟수는 세션 안에서만 센다. 재개 세션에서 다시 0부터 세도 재개는 사용자가 시작하므로 무한 반복이 되지 않는다.

`중단` 보고(기대 해시 불일치)는 도구 오류가 아니다. 누가 입력을 바꿨는지 확인하고 해시를 다시 계산해 새 회차로 배정한다.

### Phase 4 — 엮기

`learning-editor` 1명. 전 챕터의 현재 판본이 검수를 통과한 뒤에만 시작한다. 최종 확정은 편집과 재검수가 끝난 뒤다.

시작 전에 지휘자가 확인한다. **오류가 하나라도 있으면 엮기를 배정하지 않는다** — 낡은 판정 위에서 엮으면 검수받지 않은 문장이 책에 들어간다.

```bash
python3 ~/.claude/orchestration/book.py check <출력경로> --stage review
```

넘기는 것: 출력 경로 전체 · 설계서 · 모든 검수 리포트의 S3 항목(귀속 `원고`만) · 원고에 `확인 필요` 표시가 남은 챕터의 정확성 리포트.

에디터가 **하지 않는 것**: 새 내용 추가, 사실 판단. 설명이 틀렸다고 판단되면 고치지 말고 「지휘자 보고」 절에 적는다. `확인 필요` 표시는 정확성 리포트가 그 줄에 답했을 때만, 주석만 지운다 — 판단은 이미 검수자가 했다(산출물 계약 3절 「확인 필요 표시」). review 게이트의 경고가 지울 표시를 알려 준다.

편집은 **라운드** 단위로 돈다. 한 라운드 = 편집자 1회 배정 → 그 편집이 바꾼 판본 전부의 묶음 재검수.

1. 편집자의 변경 파일·보고를 받고 `--stage draft`로 구조와 링크를 확인한다. 첫 라운드는 남은 `확인 필요` 표시를 모두 정리하는 라운드이기도 하다
2. **묶음 재검수.** 이번 라운드에 편집된 챕터(`계기: 편집`)와, 선수 본문이 바뀌어 검수입력해시가 달라진 후행 챕터(`계기: 입력 변경`)를 한 묶음으로 두 독립 검수자에게 배정한다. 동시 작업자 3명 한도 안에서 나눠 돌리되, **묶음 전체가 끝나기 전에는 다음 편집을 배정하지 않는다** — 한 장씩 편집·재검수를 오가면 이미 검수한 후행 장이 다음 편집으로 또 낡는다
3. 재검수에서 S1이 나온 챕터는 Phase 3 게이트대로 Phase 2로 되돌린다. 설계 누락·사실 의심은 해당 설계자·집필자·검수자에게 돌린다
4. S3이나 연결 문제가 남았으면 다음 라운드를 배정한다. **편집 라운드는 챕터당 2회까지다**(`tally`의 `편집`). 첫 라운드가 표기·중복·연결을 맞추고 둘째 라운드가 재검수가 짚은 이음매를 고친다. 셋째가 필요하다면 편집이 연결이 아니라 내용을 건드리고 있다는 신호다. 2회를 채운 챕터에 남은 S3는 「남은 것」으로 넘기고, 남은 문제가 내용이면 Phase 2로 돌린다
5. `index.md`의 미처리 항목을 최신 판정과 `미확인-수락.md`에 맞게 편집자가 갱신한다. 묶음 재검수로 판정이 바뀌었으면 마지막 재검수 뒤에 다시 맞춘다 — 열린 지적의 추적 키가 「남은 것」에서 빠지면 final 게이트가 막는다. `index.md`만 바꾸는 배정은 라운드로 세지 않는다. `--stage final` 통과 후 상태 파일에서 확정한다

원고의 frontmatter를 `확정`으로 고쳐 상태를 표시하지 않는다. 메타데이터 변경도 원고 해시를 바꾸므로 작업 상태는 `.교재상태.json`에서만 관리한다.

### Phase 5 — 인계

`book.py check <출력경로> --stage final`을 통과한 뒤 지휘자가 보고한다. 오류가 남으면 완료 대신 진행 상황과 막힌 항목을 보고한다.

- 만든 것: 챕터 수 · 총 분량 · 예상 학습 시간 · `index.md` 경로
- 원래 목차에서 바꾼 것
- 남은 것: 미해결 S2/S3, 수락한 미확인, 에디터가 올린 사실 의심 항목, 집필자들의 「이월 제안」, `blocked` 챕터와 필요한 것
- 다음에 할 수 있는 것 (예: `/교재 검수`, 특정 챕터 재집필)

#### 미확인을 물을 때

검수자가 확인하지 못한 핵심 사실(리포트의 「미확인」)은 **사용자가 수락하지 않으면 완료로 보고하지 않는다.** final 게이트가 기계로 막는다.

- 묻는 시점은 Phase 4 시작 전에 한 번, final 게이트가 막혔을 때 한 번이다. 챕터마다 따로 묻지 않고 묶어서 묻는다
- 각 행의 추적 키 · 리포트 경로 · 「확인하지 못한 것」과 「확인할 방법」을 그대로 보이고, 선택지를 준다: **근거를 준다**(→ 설계자가 계약에 넣거나 집필자가 원고에 반영, 재검수) / **그 사실을 뺀다**(→ 계약 수정) / **미확인인 채로 둔다**(수락)
- 수락이면 지휘자가 `미확인-수락.md`에 그 판본의 행을 더한다(산출물 계약 7절). 답이 없으면 더하지 않는다 — 침묵은 수락이 아니다
- 수락한 미확인은 `index.md` 「남은 것」과 최종 보고에 남긴다

단일 파일로 읽고 싶다는 요청이 있으면 합본을 만든다. **합본은 재생성물이다** — 직접 고치지 않는다. 고칠 것이 있으면 챕터를 고치고 다시 만든다.

```bash
python3 ~/.claude/orchestration/book.py build <출력경로>
```

## 되돌림 · 재개

**되돌림**은 Phase 3·4 → 2(본문, 귀속 `원고`), → 1(계약, 귀속 `계약` — 설계 검수를 다시 거친다), → 3(편집 후 재검수)이다. 편집 이후 발견된 결함도 해결·재검수하기 전에는 확정하지 않는다.

**재개**는 `.교재상태.json`을 읽고 실제 파일·입력해시·검수해시를 대조한다. 상태는 작업 이력이고 검증 통과를 대신하지 않는다. 어긋나면 최신 파일을 검사해 stale/미완료로 복구한다. 파일이 있다는 이유만으로 통과 처리하지 않는다. 재집필·편집 횟수와 열린 지적은 `tally`로 다시 세어 덮어쓰고, `blocked`는 그 이유가 아직 유효한지 — 계약버전이 그대로인지 — 보고 유지하거나 푼다.

## 배치 원칙

- **배정은 「배정 메시지」 형식으로 한다** (→ 산출물 계약 「6. 배정 메시지」). 절차를 메시지에 복사하지 말고 스킬 경로만 준다. 입력은 경로로 주고 내용을 붙여넣지 않는다
- **띄울 때 `model`·`effort` 인자를 넘기지 않는다.** 역할 파일 frontmatter가 정한다. 두 검수자는 같은 등급이다 — 한쪽만 낮추면 두 축의 판정 깊이가 달라져 리포트를 나란히 놓고 볼 수 없다
- **두 작업자가 같은 파일을 동시에 소유하지 않는다.** 배정 메시지의 `쓸 수 있는 파일`이 소유권이고, 그 밖은 읽기 전용이다
- **집필자·검수자 한 작업에는 한 챕터.** 설계자와 편집자는 책 전체를 맡는다
- **읽기 전용 역할에는 쓰기 경로를 하나만 준다.** 검수자는 `검수/` 밖에 쓰지 않는다
- 내용상 같은 실패가 반복되면 계약 또는 작업 범위를 재검토한다(→ 「막혔을 때」). 일시적인 도구 오류는 원고나 계약을 바꾸지 않고 2회까지 다시 보낸다(→ 「도구 오류」)
- 서브에이전트 결과는 사용자에게 자동으로 보이지 않는다. 지휘자가 **옮겨 적는다**

## 훅 — 보조 계층

에이전트 5개와 `교재` 스킬의 frontmatter가 `~/.claude/orchestration/hook.py`를 부른다. 훅은 위 규칙을 대신하지 않는다 — 소유권은 배정 메시지가, 통과는 게이트가 정한다. 그중 **검수 독립성을 깨는 쓰기만 막고** 나머지는 남기기만 한다.

| 언제 | 하는 일 |
|---|---|
| 쓰기 전 | 막는다: 지휘자의 `검수/`·`chapters/`·`00-설계/` 쓰기, 검수자의 `검수/` 밖 쓰기, 나머지 작업자의 `검수/`·`미확인-수락.md` 쓰기, 누구든 `.교재기록.jsonl` 쓰기. 허용한다: `book.py`의 점검 명령(`check`·`inputs`·`review-inputs`·`tally`·`hash`, 지휘자는 `build`까지)은 권한을 묻지 않는다 |
| 쓴 뒤 | `.교재기록.jsonl`에 한 줄 남긴다(산출물 계약 8절) |
| 작업자가 끝날 때 | 그 작업자가 쓴 파일과 배정된 파일(`쓸 수 있는 파일`)만 `book.py check`로 보고 결과를 알린 뒤 기록한다. **막지 않는다** — 판정은 지휘자의 게이트가 한다 |

- 범위는 책 작업 공간(`.교재상태.json`이 있는 디렉터리) 안의 Write·Edit다. Bash로 쓰는 것은 막지 못한다. 종료 점검은 배정 메시지의 `쓸 수 있는 파일`도 보므로 Bash로 고친 배정 파일도 점검하고, 작업 중 바뀐 것은 `도구: 미상`으로 남긴다(산출물 계약 8절). 배정 밖의 Bash 쓰기는 남지 않는다. OS 수준의 접근 통제가 아니다
- 훅이 막았으면 우회하지 않는다. 막힌 쓰기는 배정이 잘못됐다는 신호다 — 그 파일의 담당자에게 배정한다
- 지휘자 쪽 훅은 `교재` 스킬이 불린 세션에서만 걸리고, 불린 뒤로는 그 세션의 다음 턴에도 남는다. 스킬 없이 이 파일만 읽고 지휘하면 기록과 차단이 없다
- 에이전트 훅은 세션이 시작될 때 읽힌다. 에이전트 frontmatter를 고쳤으면 새 세션에서야 걸린다
- 훅이 설치되지 않았거나 실패해도 작업은 막히지 않는다. 게이트는 그대로 돈다
