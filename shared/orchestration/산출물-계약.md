# 산출물 계약

> **레이어: 오케스트레이션** — Phase 사이를 건너는 물건의 규격.
> 이 파일이 담지 않는 것: 각 칸을 **어떻게 채우는지**(→ 스킬). 여기 있는 것은 **무엇이 들어 있어야 하는지**뿐이다.

에이전트들은 서로를 모른다. 앞 단계가 누구였는지, 뒤에서 누가 받을지 모른 채 **이 규격만 보고** 일한다. 그래서 규격이 흔들리면 팀이 흔들린다. 규격을 바꾸려면 이 파일을 먼저 고치고, 그다음 스킬을 고친다.

## 공통 명명

- 챕터 번호는 **두 자리 0 패딩**: `01`, `02` … `12`
- 챕터 파일: `chapters/NN-<슬러그>.md`. 슬러그는 한글 허용, 공백은 `-`
- 계약: `00-설계/챕터계약/NN.md`
- 검수: `검수/NN-정확성.md`, `검수/NN-독자.md`
- 모든 경로는 **출력 경로 기준 상대 경로**로 적는다

Frontmatter는 한 줄 스칼라, 인라인 문자열 목록(`[]`), 들여쓴 문자열 목록만 쓴다. 중첩 객체·YAML 앵커·여러 줄 스칼라는 지원하지 않고 중복 키는 오류다. 여러 줄 설명은 본문으로 옮긴다.

내부 링크는 `[표시](상대경로#앵커)`만 쓴다(참조형 링크 불가, 공백·괄호는 URL 인코딩). 앵커는 소문자·문장부호 제거·공백을 `-`로 바꾸고 같은 제목의 두 번째부터 `-1`, `-2`가 붙는다. 코드 안의 예시는 변환 대상이 아니다.

## 1. 챕터 계약서 — `00-설계/챕터계약/NN.md`

`curriculum-architect`가 쓰고, `chapter-writer`·검수자 전원이 읽는다. **집필자가 받는 유일한 지시서**다. 여기 없는 것은 쓰지 않고, 여기 있는 것은 빠뜨리지 않는다.

```markdown
---
번호: "03"
제목: 커넥션 풀은 왜 크게 잡으면 느려지는가
슬러그: 커넥션-풀-크기
선수챕터: ["01", "02"]
목차항목: ["2.3", "2.4"]
분량: 4000~5500자
읽기시간: 30분
계약버전: 1
---

## 한 줄 목표
<이 챕터를 다 읽은 독자가 새로 할 수 있게 되는 것 한 문장>

## 다 읽으면 답할 수 있는 질문
1. <질문>
2. <질문>
3. <질문>                     ← 2~3개. 본문의 소제목과 1:1로 대응한다

## 다루는 것
- <항목>

## 다루지 않는 것
- <항목> → **05장 소유**       ← 반드시 소유 챕터 번호를 적는다

## 관통 사례에서 쓰는 장면
<설계서가 정한 사례 중 이 챕터가 쓰는 부분. 새 사례를 만들지 않는다>

## 필수 포함
- 코드 예시: 2개 (<어떤 지점인지>)
- 도식: 1개 (<무엇을 그리는지>) / 불필요면 "없음"
- 오해 짚기: 1개 이상
- 면접 포인트: 있음 / 없음

## 이어받을 문장
<앞 챕터가 남긴 문제. 첫 문단이 이것을 받아서 시작한다>

## 넘길 것
<다음 챕터에 남기는 미해결 문제 한 줄>

## 이 챕터에서 처음 정의하는 용어
- <용어> (<영문 병기>)

## 근거 확인 필요 항목
- <버전에 따라 달라지는 동작 · 수치 · 최신 동향>   ← 집필자는 추정하지 말고 표시만 한다
```

- `다루지 않는 것`에는 **소유 챕터 번호**가 있어야 한다. 번호가 없으면 집필자는 "그럼 내가 쓸까"로 기운다
- `목차항목`은 번호를 붙인 `목차.md`의 항목 번호다. 모든 항목을 적어도 한 계약에 배정한다. 추가 연결 챕터만 `[]`를 허용한다
- `근거 확인 필요 항목`은 집필자에게 **모른다고 말할 자리**다. 추정이 곧 S1이 되는 것(기본값·버전별 동작·수치)을 설계 단계에서 지목한다. 집필자는 `<!-- 확인 필요: … -->`로 남기고 검수자는 이 목록부터 검증한다

게이트: `book.py check <출력경로> --stage plan`

## 2. 챕터 파일 — `chapters/NN-<슬러그>.md`

`chapter-writer`가 쓰고, 검수자가 읽고, `learning-editor`가 연결만 손댄다.

```markdown
---
번호: "03"
제목: 커넥션 풀은 왜 크게 잡으면 느려지는가
계약버전: 1
입력해시: <book.py inputs 출력경로 03 의 SHA-256 출력값>
요약: <다음 챕터 집필자가 받을 한 줄. 이 챕터가 해결한 것 + 남긴 문제>
이월제안:
  - <계약 밖이지만 다뤄야 할 것 같은 항목 / 없으면 빈 목록>
---
```

- `요약` — 다음 챕터 집필자에게 넘어가는 **유일한 앞 문맥**. 본문 요약이 아니라 바통이다: 무엇을 해결했고 무엇을 남겼는지
- `이월제안` — 계약을 벗어나지 않으면서 발견한 것을 버리지 않는 칸. 지휘자가 Phase 5에서 모아 보고한다
- `입력해시` — 계약·설계서·모든 선수 챕터 `요약`을 묶은 값(`book.py inputs`). 입력을 읽기 전에 계산해 두고 완료할 때 다시 비교해, 달라졌으면 완료로 넘기지 않는다. **해시만 새로 적어 이전 원고를 유효하게 만들지 않는다**
- **작업 상태를 원고에 적지 않는다.** `.교재상태.json`에만 둔다 — 원고 메타데이터를 고치면 해시가 바뀌어 검수 판정이 무효가 된다

## 3. 검수 리포트 — `검수/NN-정확성.md` · `검수/NN-독자.md`

검수자가 쓰고, 재집필하는 `chapter-writer`와 지휘자가 읽는다. **검수자는 본문을 고치지 않는다. 리포트가 유일한 출력이다.**

```markdown
---
대상: chapters/03-커넥션-풀-크기.md
대상해시: 9f2b…   # 검수한 그 판본의 SHA-256
계약해시: 7a1c…   # 검수한 계약 파일 전체의 SHA-256
검수입력해시: 4bc8…  # book.py review-inputs 출력경로 03 의 출력값
축: 정확성 | 독자
계약버전: 1
S1: 1
S2: 1
S3: 0
---

## 판정
재집필 필요 | 수정 권고 | 통과

| ID | 심각도 | 위치 | 무엇이 문제인가 | 제안 |
|---|---|---|---|---|
| S1-1 | S1 | L42 | `maximumPoolSize` 기본값을 20이라고 단정. HikariCP 기본값은 10 | 값을 고치고 버전을 명시 |
| S2-1 | S2 | L88 | 근거 없이 "대부분의 서비스에서" | 수치나 조건을 붙이거나 단정을 낮춘다 |

## 계약 대조
- 질문·소유 범위·필수 포함 대조 결과. 추가 결함이 있으면 위 표에도 ID를 부여한다
```

**`대상해시`는 판정의 유효기간이다.** 검수를 시작하기 전에 계산해서 적는다.

```bash
python3 ~/.claude/orchestration/book.py hash chapters/03-커넥션-풀-크기.md
python3 ~/.claude/orchestration/book.py hash 00-설계/챕터계약/03.md
python3 ~/.claude/orchestration/book.py review-inputs <출력경로> 03
```

원고가 한 글자라도 바뀌면 판정은 그 순간 무효다. 해시 없이 적힌 `S1: 0`은 어느 판본을 본 숫자인지 알 수 없으므로 통과의 근거가 되지 못한다.

`검수입력해시`는 설계서와 선수 챕터 **본문 전체**를 묶는다. 선수 본문이 바뀌면 `요약`이 그대로여도 판정은 낡는다. 두 검수자 모두 시작과 종료 시 값을 확인한다.

### 심각도

| 등급 | 기준 | 지휘자의 처리 |
|---|---|---|
| **S1** | 틀린 사실 · 동작하지 않는 코드 · 계약 위반(질문 미응답, 다른 챕터 침범) · 앞 챕터 지식만으로 따라갈 수 없음 | Phase 2로 되돌림 |
| **S2** | 오해를 부르는 서술 · 근거 없는 단정 · 설명 순서가 뒤집힘 · 예시 없이 추상만 이어짐 | 다음 재집필에 동봉. 단독으로 편집을 막지 않으며 남은 ID와 이유를 인계에 공개 |
| **S3** | 표현 · 용어 표기 · 문단 길이 | Phase 4로 |

**심각도는 검수자가 정한다. 지휘자가 올리거나 내리지 않는다.**

### 지적 ID

지적마다 ID를 붙인다. **재검수에서 같은 결함이 살아 있으면 같은 ID를 그대로 쓴다.** 새로 발견한 결함만 새 번호를 받는다.

- 추적 키는 `챕터번호/축/ID`다. 두 검수자의 `S1-1`은 서로 다른 지적이다
- 심각도 열에는 `S1`·`S2`·`S3`·`해결`만 쓰고, frontmatter 개수는 미해결 행만 센다. 같은 ID를 한 리포트에 두 번 쓰지 않는다
- 다른 축의 리포트는 보지 않되, 자기 축의 이전 리포트는 재검수 입력으로 받는다

되돌림 상한은 챕터가 아니라 이 ID 위에서 돈다. 몇 회에 멈추는지와 그 뒤의 처리는 파이프라인의 「막혔을 때」가 정한다.

## 4. 설계서 — `00-설계/설계서.md`

`curriculum-architect`가 쓴다. 팀 전체의 공유 기준이다.

필수 절: `학습 경로` · `의존성 그래프`(Mermaid + 레벨 표) · `관통 사례` · `용어집` · `원래 목차에서 바꾼 것` · `챕터 목록`

- **레벨 표**가 Phase 2 병렬 배치의 근거다. 없으면 지휘자는 순차로만 배치한다
- **용어집**은 `용어 | 표기 | 최초 정의 챕터` 3열. 집필자 전원이 이 표기를 그대로 쓴다
- **원래 목차에서 바꾼 것**은 사용자 승인 화면에 그대로 올라가므로 이유가 한 줄씩 붙어야 한다

## 5. 상태 파일 — `.교재상태.json`

**지휘자 전용.** 에이전트는 읽지도 쓰지도 않는다.

```json
{
  "책": "JVM 메모리 구조",
  "출력경로": "./jvm-memory",
  "목차원본": "./목차.md",
  "독자": "실무 4년차 Java·Spring 백엔드",
  "깊이": "표준",
  "phase": 2,
  "챕터": [
    { "번호": "03", "제목": "...", "선수": ["01","02"], "레벨": 1,
      "status": "집필중", "재시도": 1, "S1": 1, "S2": 2,
      "열린지적": { "03/정확성/S1-1": 2, "03/독자/S2-3": 1 } }
  ],
  "갱신": "2026-09-22T15:40:00+09:00"
}
```

`status`: `계약완료` → `집필중` → `초안` → `검수중` → `검수완료` → `편집중` → `재검수중` → `확정`. `확정`은 final 게이트 통과 후에만 쓴다. 되돌림은 `초안`으로 되돌리고 `재시도`를 1 올린다.

여기에 두 값이 더 있다. 어떤 조건에서 이 값이 되는지는 파이프라인의 「판정이 무효가 되는 때」와 「막혔을 때」가 정한다.

- **`stale`** — 원고는 있지만 근거가 낡았다. 확정으로 세지 않는다
- **`blocked`** — 그 챕터는 멈추고 나머지는 계속 간다. `막힘` 필드에 이유와 필요한 것을 적는다

`열린지적`은 지적 ID별 살아남은 횟수다. 되돌림 판정의 근거이므로 리포트를 받을 때마다 갱신한다.

재개할 때 상태와 실제 파일이 어긋나면 파일·입력해시·검수해시를 다시 검사해 상태를 복구한다. 파일 존재만으로 확정하지 않는다.

## 검증 명령

어느 단계에서 무엇을 돌리는지는 파이프라인의 각 Phase가 정하고, 사람이 쓰는 전체 목록은 `claude/CLAUDE.md`에 있다. 계약이 정하는 것은 **무엇이 일치해야 통과인가**뿐이다.

- `--stage plan` — 계약 필드·목차 대응·선수 참조·순환
- `--stage draft` — 원고·`요약`·`계약버전`·`입력해시`·링크
- `--stage review` — 위 조건 + 두 축 리포트 각 1개, 대상·계약 판본과 지적 개수 일치, S1 0건
- `--stage final` — 책 전체 검수 통과 + `index.md`의 전 챕터 링크, 미해결 `확인 필요` 없음

**내용의 정확성과 교육적 품질은 이 검사가 판정하지 않는다.** 그건 검수자의 일이다.

## 6. 배정 메시지 — 지휘자 → 작업자

서브에이전트는 이 대화를 보지 못한다. 배정 메시지 하나만 보고 일한다. 그래서 형식이 고정돼 있다.

```text
작업 ID:    write-03-r1
역할:       chapter-writer
절차:       ~/.claude/skills/챕터-집필/SKILL.md
작업 공간:  /Users/…/jvm-memory          ← 절대 경로
목표:       03장 원고 한 편. 계약의 질문 3개에 답한다
입력:       00-설계/챕터계약/03.md
            ~/.claude/instructions/교재-공통규약.md
            00-설계/설계서.md 의 「용어집」·「관통 사례」 절
            02장 frontmatter 의 `요약` 한 줄
쓸 수 있는 파일: chapters/03-커넥션-풀-크기.md
완료 조건:  스킬의 자가 점검 전 항목 통과, frontmatter `요약`·`이월제안` 채움
보고:       손댄 절 · 미처리 항목과 이유 · 새 이월제안
```

지켜야 할 것 네 가지.

- **절차를 복사하지 않는다.** 스킬 경로만 준다. 메시지에 절차를 적으면 두 곳에 생기고 한쪽만 고쳐진다
- **입력은 경로로 준다.** 붙여넣은 내용은 파일이 바뀌어도 그대로 남아 낡은 입력으로 일하게 만든다
- **`쓸 수 있는 파일`이 곧 소유권이다.** 그 밖은 읽기만 한다. 두 작업자가 같은 파일을 동시에 소유하지 않는다
- **작업 ID에 회차를 넣는다**(`-r1`, `-r2`). 횟수는 작업자가 바뀌어도 이어서 센다
