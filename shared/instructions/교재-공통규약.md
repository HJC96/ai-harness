# 교재 공통 규약

> **레이어: 공유 규약** — 집필·검수·엮기 세 스킬이 같이 보는 기준.
> 이 파일이 담지 않는 것: 작업 순서(→ 스킬), 팀 배치(→ 오케스트레이션).
>
> 한 챕터만 읽어도 다른 챕터와 같은 책처럼 보여야 한다. 병렬로 쓰는 집필자들이 서로를 모른 채 같은 결을 내는 근거가 이 파일이다.

## 독자

기본값은 **실무 3~5년차 Java·Spring 백엔드 개발자**, 기술 면접 준비 병행. Phase 0에서 다른 독자가 지정되면 아래 두 가지만 그쪽에 맞춘다 — 코드 예시의 언어·대응 지점, 배경 설명의 깊이. 나머지 규약은 그대로다.

기본 독자에 대해 지키는 것 두 가지.

- **이미 아는 것을 다시 가르치지 않는다.** "애너테이션이란", "HTTP란" 수준은 이 독자에게 소음이다. 배경 보충은 실무에서 만났을 리 없는 개념에만 짧게 붙인다. 단, 흔한 용어를 자료가 일상 용법과 **다른 뜻으로** 쓰면 그 어긋남은 반드시 짚는다
- **개념이 코드에 닿는 지점을 지나치지 않는다.** 원리를 문장으로만 아는 것과, 그것이 `@Transactional` 한 줄이나 설정값으로 드러나는 걸 본 것은 이해의 깊이가 다르다

## 문체

- **평서체(`~한다`)**. 존댓말·구어체 금지
- 한 문단은 3~5문장. 한 문장에 주장 하나
- 결과만 말하지 말고 **왜 그 결과가 나오는지** 밝힌다
- 안전성 · 성능 · 비용 · 복잡성은 섞지 말고 구분한다
- 주요 설계 결정마다 **얻는 것 / 잃는 것**을 명시한다
- 공식이 나오면 공식보다 **각 변수가 무엇이고 값이 변하면 동작이 어떻게 달라지는지**

**쓰지 않는 표현** — 번역체와 AI 상투어. `~에 대해서`, `~을 통해`, `~라고 할 수 있다`, `중요한 역할을 한다`, `핵심은 ~이다`로 문단을 여는 것, 근거 없는 3항목 나열, "결론적으로 ~는 매우 중요합니다" 류의 마무리. 항목이 실제로 셋일 때만 셋을 쓴다.

## 용어

- 설계서 「용어집」의 표기를 **그대로** 쓴다. 같은 개념에 다른 표기를 쓰지 않는다 (커넥션 풀 ↔ 커넥션풀 ↔ connection pool)
- 한글 표기 우선, **최초 1회만** 영문 병기: 커넥션 풀(connection pool)
- 그 챕터가 처음 정의하는 용어인지는 계약의 「처음 정의하는 용어」로 판단한다. 남의 용어를 다시 정의하지 않는다

## 코드 예시

붙이는 기준: **개념이 실제 코드에서 모습을 드러내는 지점.** 문법 설명이나 장식용 코드는 붙이지 않는다.

- 기본 스택 Java 17 · Spring Boot 3.x. 버전에 따라 달라지는 동작은 버전을 명시한다
- **20줄 이내**, 그 개념과 무관한 줄은 지운다. import·게터 생략
- 주석은 "무엇을 하는지"가 아니라 **"여기가 그 개념이 드러나는 자리"**를 가리킬 때만
- 동작하지 않는 코드는 S1이다. 의사코드는 ```text 로 표시한다

## 형광펜

이 하네스의 기본 기준은 아래 표다. 다른 개인 스킬 설치 여부에 따라 규약이 바뀌지 않는다. 사용자가 별도 형광펜 기준을 지정하면 요청 입력에 그 경로를 기록하고 적용한다.

| 색 | 칠하는 것 | 소단원당 |
|---|---|---|
| 🟡 `#FFF3B0` | 결론 · 정의 · 원리 | 1개 |
| 🟢 `#D3F9D8` | 근거 · 사례 · 수치 | 2개 |
| 🔴 `#FFC9C9` | 주의 · 오해 · 트레이드오프 | 1개 |

- **중요도 3단계가 아니라 정보의 종류다**
- 소단원당 합계 **3개를 넘지 않는다**
- **노랑만 이어 읽으면 그 챕터의 요약이 되어야 한다.** 개수 제한보다 이 기준이 위에 있다
- 본문을 다 쓴 **뒤에** 칠한다. 쓰면서 칠하면 반드시 넘친다
- 제목 · 코드블록 · 표 안에는 칠하지 않는다

**💬 여백 메모**는 형광펜이 아니다. 문서가 답을 줄 수 없는 것 — 자기 코드·자기 서비스로 돌아가야 답할 수 있는 **질문**만. 소단원당 1개, 블록쿼트 한 줄.

문법은 인라인 `<mark style="background-color:#FFF3B0">…</mark>`가 기본. 사용자가 GitHub·Notion을 언급했으면 문장 앞 이모지 마커로 바꾸고 범례를 챕터 앞에 둔다.

## 챕터 구조

```markdown
# N. <질문형 제목>

<앞 챕터에서 이어받는 1~2문장>

## N.1 <독자가 실제로 가질 만한 질문 형태의 소제목>
...
## 다 읽고 나면
- 답할 수 있게 된 질문 (계약의 질문 그대로)
- 다음 챕터로 넘기는 문제 한 줄
```

- 모든 제목에 번호: `# 3.` / `## 3.1` / `### 3.1.1`
- 소제목은 **질문 형태**로
- 각 개념은 **문제 → 기존 방식의 한계 → 원리 → 사례에서의 동작 → 얻는 것과 잃는 것 → 흔한 오해** 흐름을 자연스러운 글로 녹인다. 이 항목들을 소제목으로 끊어 나열하지 않는다
- 절이 바뀌기 전 1~2문장: 앞에서 해결한 것 / 남은 문제 / 다음이 필요한 이유
- **앞에서 한 약속은 뒤에서 지킨다.** "뒤에서 다루겠다"고 썼으면 실제로 다루거나, 그 챕터 번호를 적는다

## 면접 포인트

계약에 `면접 포인트: 있음`이면 해당 절 끝에 한 줄로 표시하고, 챕터 끝 `## 다 읽고 나면` 앞에 예상 질문 1~2개와 **꼬리질문 한 단계**를 붙인다. 답 전문을 쓰지 말고 **답변 뼈대**만 쓴다.
