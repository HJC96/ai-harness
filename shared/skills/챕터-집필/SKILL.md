# 챕터 집필 — 계약 한 장을 본문 한 장으로

> **레이어: 스킬** — 어떤 순서로 하는가.
> 판단 기준(무엇을 자르고 무엇을 남기는가)은 `~/.claude/agents/chapter-writer.md`. 문체·코드·형광펜 규약은 `~/.claude/instructions/교재-공통규약.md`. 산출물 규격은 `~/.claude/orchestration/산출물-계약.md`.

---

## 1단계 — 받은 것만 읽는다

집필자로 배정받은 챕터와 쓰기 경로가 있어야 수행한다. 배정이 없으면 메인 세션의 오케스트레이터에 입력을 돌려준다.

입력을 읽기 전에 `python3 ~/.claude/orchestration/book.py inputs <출력경로> <챕터번호>`로 입력해시를 기록한다. 계약·설계·선수 요약을 읽고 그 입력에 맞게 집필한다.

읽는 것: **계약서** · 공통규약 · 설계서의 「용어집」과 「관통 사례」 절 · 선행 챕터 `요약` 한 줄 · (있으면) 원자료.

**다른 챕터 본문을 열지 않는다.** 궁금해도 열지 않는다. 열면 그것을 요약하며 시작하게 되고, 같은 설명이 두 챕터에 남는다. 앞 내용이 필요하면 계약의 「이어받을 문장」이 이미 그것을 담고 있다.

계약을 읽고 먼저 확인할 것 네 가지 — **질문 몇 개인가 · 무엇을 다루지 않는가 · 필수 포함이 무엇인가 · 근거 확인이 필요한 항목이 무엇인가.** 앞의 셋이 완성 판정 기준이고, 넷째는 **추정하면 안 되는 자리**의 목록이다.

## 2단계 — 뼈대를 먼저 세운다

계약의 질문을 그대로 소제목으로 편다. **질문 1개 = 소제목 1개**가 기본형이다.

```markdown
# 3. 커넥션 풀은 왜 크게 잡으면 느려지는가

## 3.1 풀을 키웠는데 응답이 느려지는 일이 왜 생기는가   ← 질문 1
## 3.2 대기는 어디서 발생하는가                          ← 질문 2
## 3.3 그래서 몇 개로 잡아야 하는가                       ← 질문 3
## 다 읽고 나면
```

각 소제목 아래에 **이 절의 결론을 한 줄로 미리 적어 둔다.** 본문을 쓴 뒤 그 줄이 노랑 형광펜 후보가 된다. 결론이 한 줄로 안 써지면 그 절은 아직 무엇을 말할지 정해지지 않은 것이다 — 쓰기 전에 정한다.

## 3단계 — 본문을 쓴다

각 개념을 다음 흐름으로 **자연스러운 글에 녹인다.** 이 항목들을 소제목으로 끊어 나열하지 않는다.

> 문제 → 기존 방식의 한계 → 핵심 원리 → 관통 사례에서의 동작 → 얻는 것과 잃는 것 → 흔한 오해

- 첫 문단은 계약의 「이어받을 문장」을 받아서 시작한다
- 관통 사례는 **계약이 배분한 장면만** 쓴다. 새 사례를 만들지 않는다. 한 장면으로 부족하면 같은 사례를 정상 · 실패 · 극단 · 복구로 변주한다
- 절이 바뀌기 전 1~2문장으로 잇는다: 앞에서 해결한 것 / 남은 문제 / 다음이 필요한 이유
- 계약의 「다루지 않는 것」에 걸리면 **한 줄 + 소유 챕터 번호 참조**로 끝낸다

```markdown
커넥션 누수 자체를 어떻게 잡는지는 7장에서 다룬다. 여기서는 누수가 있으면
풀 크기 계산이 의미를 잃는다는 것까지만 짚는다.
```

- 계약의 「근거 확인 필요 항목」과, 그 밖에 확실하지 않은 수치·기본값·버전별 동작은 `<!-- 확인 필요: HikariCP 기본 poolSize -->`로 표시하고 넘어간다. **지어내지 않는다**
- **출처를 지어 붙이지 않는다.** 분야의 안정된 지식은 그대로 설명하면 된다. 없는 근거를 꾸미면 검수자가 그 출처를 확인하러 갔다가 없다는 것만 알게 되고, 그 챕터의 나머지 문장까지 의심받는다

## 4단계 — 코드와 도식을 붙인다

계약의 「필수 포함」이 지정한 개수와 지점을 따른다. 규칙은 공통규약의 「코드 예시」·「도식」.

코드를 붙이기 전에 한 번 묻는다. **이 코드를 지우면 독자가 잃는 것이 있는가?** 없으면 장식이다.

## 5단계 — 형광펜을 칠한다

**본문을 다 쓴 뒤에 칠한다.** 쓰면서 칠하면 그 순간 중요해 보이는 문장마다 손이 가서 개수가 반드시 넘친다.

- 소단원당 🟡1 · 🟢2 · 🔴1, **합계 3개 이내**
- 2단계에서 미리 적어 둔 결론 줄이 🟡의 1순위 후보다
- **노랑만 이어 읽어서 챕터 요약이 되는지** 확인한다. 안 되면 개수가 아니라 결론이 흐린 것이다
- 💬 여백 메모는 소단원당 1개, **질문형으로**, 블록쿼트 한 줄

## 6단계 — 마무리 절과 frontmatter

```markdown
## 다 읽고 나면

답할 수 있게 된 질문
- <계약의 질문 1> — <한 줄 답>
- <계약의 질문 2> — <한 줄 답>

다음 장으로 넘기는 문제
- <계약의 「넘길 것」>
```

frontmatter의 `요약`을 반드시 채운다. **다음 챕터 집필자가 받는 유일한 앞 문맥이다.** 본문 요약이 아니라 바통이다.

`입력해시`에는 시작할 때 기록한 값을 쓴다. 완료 전에 다시 계산해 달라지지 않았는지 확인한다. 달라졌으면 원고를 완료로 넘기지 말고 입력 변경을 보고한다. `계약버전`도 현재 계약과 같아야 한다. 작업 상태는 지휘자의 상태 파일에 있으므로 원고에서 `확정`으로 바꾸지 않는다.

```yaml
요약: 풀 크기가 처리량의 상한을 결정하는 이유까지 왔다. 대기 시간이 어디서 쌓이는지는 아직 남았다.
```

계약 밖이지만 다뤄야 할 것 같은 항목은 `이월제안`에 적는다. 본문에는 넣지 않는다.

## 7단계 — 자가 점검

계약을 옆에 놓고 대조한다. **여기까지가 자가 점검이고, 정확성과 독자 관점은 다음 Phase의 두 사람 몫이다.**

- [ ] 계약의 질문에 **전부** 답했다. 소제목과 1:1 대응한다
- [ ] 「다루지 않는 것」을 침범하지 않았다 (한 줄 + 번호 참조는 허용)
- [ ] 「필수 포함」의 코드·도식·오해 짚기 개수를 채웠다
- [ ] 관통 사례의 배분된 장면만 썼다. 새 사례가 없다
- [ ] 용어집 표기를 그대로 썼다. 남의 용어를 다시 정의하지 않았다
- [ ] 첫 문단이 「이어받을 문장」을 받았고, 마지막이 「넘길 것」을 남겼다
- [ ] 형광펜 합계가 소단원당 3개 이내. 노랑만 읽으면 요약이 된다
- [ ] 분량이 계약 범위 안이다 (`wc -m <파일>`)
- [ ] `요약`과 `이월제안`을 채웠다
- [ ] 입력해시가 시작 시점과 같고 `book.py check <출력경로> --stage draft --chapter <번호>`가 통과했다

분량이 넘치면 자르는 순서: ① 배경 설명 ② 두 번째 코드 예시 ③ 부가적인 오해. 「필수 포함」은 마지막까지 지킨다.

## 재집필 모드

검수 리포트를 받아 같은 챕터를 다시 쓸 때.

1. **두 리포트를 다 읽는다.** 정확성 리포트와 독자 리포트를 각각 끝까지
2. **S1을 전부 처리한다.** 하나도 남기지 않는다. **지적 ID 단위로 응답한다** — 어느 ID를 어떻게 고쳤는지 보고에 적는다. 지적에 동의하지 않으면 고치는 대신 `이월제안`에 ID와 반론 근거를 적는다 — 말없이 무시하면 다음 검수에서 같은 지적이 다시 나오고 재시도 횟수만 소진된다
3. **S2는 고칠 수 있는 만큼 고친다.** 계약과 충돌하는 S2는 고치지 않고 이유를 적는다 — 계약이 우선이다
4. S3는 손대지 않는다. 엮기 단계의 몫이다
5. 고친 뒤 7단계 자가 점검을 **다시** 돌린다. S1을 고치다 계약을 벗어나는 일이 잦다
6. **검수 리포트를 수정하지 않는다.** 검수자의 소유다

지휘자에게 돌려줄 보고: **지적 ID별 처리 결과**(고침 / 미처리와 이유) · 손댄 절 · 새로 생긴 `이월제안`. 지휘자는 이 ID로 되돌림 횟수를 센다.
