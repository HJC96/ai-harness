# AI Harness — 목차로 만드는 학습서

**목차 하나를 주면, 책처럼 이어 읽히는 Markdown 학습서를 만들어 주는 AI 작업 틀(하네스)입니다.**

AI 한 명이 처음부터 끝까지 다 쓰지 않습니다. 설계하는 AI, 쓰는 AI, 검수하는 AI, 엮는 AI를 따로 두고, 서로의 일을 대신하지 않게 합니다. 특히 **쓴 AI가 자기 글을 검수하지 않습니다.** 메인 세션은 지휘만 맡습니다. 일을 나눠 주고, 단계마다 결과 파일을 스크립트로 확인하고, 사용자에게 보고합니다.

```text
목차 ──▶ 설계 ──▶ 설계 검수 ──▶ 장별 집필 ⇄ 장별 검수 ──▶ 한 권으로 엮기 ──▶ 완성
          ▲                         ▲            │
          │                         └─ 원고 탓 ──┤
          └──────── 계약(챕터 지시서) 탓 ────────┘
```

이 저장소에는 같은 목적의 구현이 두 벌 있습니다. 서로 독립적이므로 쓰는 도구에 맞는 쪽만 보면 됩니다 → [Claude Code](#claude-code로-사용하기) · [Codex](#codex로-사용하기)

| | Claude Code | Codex |
| --- | --- | --- |
| 설치 | `bash scripts/install-claude.sh` | `bash scripts/install-codex.sh` |
| 시작 | 아무 폴더에서 새 세션 → `/교재 <목차>` | 이 저장소에서 `codex` 실행 후 요청 |
| 결과물 | 장별 파일 + `index.md` (원하면 합본) | `book.md` 한 파일 |
| 검수 | 정확성·독자 두 검수자가 따로 | 검토자 한 명 + 조사 담당 |
| Python | 3.9 이상 | 3.11 이상 |
| 자세한 규칙 | [claude/CLAUDE.md](claude/CLAUDE.md) | [codex/AGENTS.md](codex/AGENTS.md) |

견본이 궁금하면 테스트용으로 만들어 둔 3장짜리 책 [tests/fixtures/견본/](tests/fixtures/견본/index.md)을 보면 됩니다.

## Claude Code로 사용하기

### 1. 설치 (한 번만)

```bash
git clone <이 저장소> && cd ai-harness
bash scripts/install-claude.sh            # ~/.claude 에 역할·스킬·지휘 파일·공통규약 링크를 만든다
bash scripts/install-claude.sh --check    # 설치된 링크가 맞는지 확인
```

설치는 `~/.claude` 안에 이 저장소 파일을 가리키는 **링크**를 만듭니다. 그래서 저장소 파일을 고치면 다음 세션부터 반영됩니다. 이미 있는 내 파일과 충돌하면 아무것도 설치하지 않고 멈추며, 전역 `CLAUDE.md`나 권한 설정은 건드리지 않습니다. 설정 디렉터리를 바꿔 쓴다면 `CLAUDE_CONFIG_DIR=/절대/경로`를 앞에 붙입니다. 지울 때는 `--uninstall`을 씁니다. 이 하네스가 만든 링크만 지웁니다.

### 2. 책 만들기

설치가 `~/.claude`에 되므로 이 저장소 안에서 열 필요는 없습니다. **책을 둘 폴더에서 새 Claude Code 세션을 열고** 목차를 줍니다. 상대 경로는 그 폴더 기준입니다.

```text
/교재 아래 목차로 책을 만들어줘. 독자는 자바 1년차, 출력은 ./jvm-memory
1. JVM 메모리 구조
2. 힙과 GC
3. 메모리 누수 찾기
```

목차는 붙여 넣어도 되고 파일 경로나 사진·PDF로 줘도 됩니다. 시작 전에 다음 네 가지를 정하는데, 빠진 것만 묻습니다.

| 입력 | 안 주면 |
| --- | --- |
| 목차 | 필수. 책 제목만 주면 목차를 지어내지 않고 되묻습니다 |
| 독자 | 기본 독자(실무 3~5년차 Java·Spring 백엔드)로 두고, 그렇게 가정했다고 알려 줍니다 |
| 출력 경로 | `./<책이름>/`을 제안합니다 |
| 깊이 | `표준`. 짧게는 `압축`, 자세히는 `정밀` |

중간에 멈춰도 산출물에서 이어 갈 수 있습니다.

```text
/교재 이어서 ./jvm-memory        # 끊긴 곳부터 다시
/교재 상태 ./jvm-memory          # 어디까지 했는지만 본다 (아무것도 바꾸지 않는다)
/교재 설계 <목차>                # 설계와 설계 검수까지만
/교재 검수 ./jvm-memory          # 이 하네스로 만든 원고를 검수만
/교재 재집필 ./jvm-memory 02     # 02장을 다시 쓰기 (숫자는 챕터 번호)
```

**시간과 사용량.** 장마다 집필 1회와 검수 2회가 돌고, 설계·설계 검수·편집·재검수가 더해집니다. 2장짜리 목차를 실제로 돌렸을 때 서브에이전트 호출이 10~18회였습니다. 장 수가 늘면 그만큼 늘어납니다. 권한 모드에 따라 파일 쓰기마다 확인 창이 뜰 수 있습니다(`book.py` 점검 명령은 역할 훅이 허용합니다).

### 3. 사용자가 할 일

대부분 알아서 진행되고, 사용자 판단이 필요한 때만 멈춰서 묻습니다.

1. **설계 확인** — 챕터 목록과 장별 예상 시간, 원래 목차에서 바꾼 것(합침·나눔·순서 변경과 각 이유), 전 챕터를 관통하는 예시 하나, 총 분량을 보여 줍니다. 목차를 빼거나, 범위를 넓히거나, 학습 순서를 바꾸는 변경은 승인을 받고 나서 진행합니다. 집필 중에 계약을 고치다 범위나 순서가 바뀌어도 다시 묻습니다.
2. **확인하지 못한 사실** — 검수자가 근거를 찾지 못한 핵심 사실은 챕터마다 따로 묻지 않고 엮기 전에 묶어서 묻습니다(최종 검사에서 새로 걸리면 한 번 더). "근거를 준다 / 그 내용을 뺀다 / 미확인인 채로 둔다" 중에서 고르면 됩니다. 답하지 않으면 수락으로 보지 않고, 수락하지 않은 사실이 남아 있으면 완성으로 보고하지 않습니다.
3. **막힌 챕터** — 같은 지적이 두 번 고쳐 써도 남거나 한 챕터를 네 번 다시 써도 해결되지 않으면, 그 챕터(와 그 장을 선수로 둔 장)를 멈추고 이유와 필요한 것을 알려 줍니다. 나머지 챕터는 계속 갑니다. 강제로 통과시키지는 않습니다. 필요한 사실을 알려 주거나, 계약 범위를 줄이거나, 챕터를 빼는 것 중에서 같이 정합니다.
4. **완성 보고** — 만든 것(챕터 수·분량·학습 시간), 원래 목차에서 바꾼 것, 남은 것을 보고하면 끝입니다. `index.md`를 열어 읽기 시작하면 됩니다.

### 4. 결과물

```text
jvm-memory/
  index.md                 ← 여기서 시작. 읽는 순서·챕터 표·학습 지도·용어 색인·남은 것
  chapters/
    01-jvm-메모리-구조.md   ← 본문
    02-힙과-gc.md
  00-설계/
    설계서.md              ← 학습 경로·의존성 그래프·용어집
    챕터계약/01.md …        ← 챕터별 지시서 (무엇을 다루고 무엇을 다루지 않는가)
  검수/
    설계-정확성.md  설계-독자.md   ← 집필 전 설계 검수
    01-정확성.md  01-독자.md       ← 챕터별 검수 리포트 (판정·지적·근거)
  목차-원문.md  목차.md     ← 받은 목차 원문과 번호를 붙인 판
  미확인-수락.md            ← 사용자가 수락한 미확인 사실 (수락이 있을 때만)
  .교재상태.json            ← 진행 상태 (이어서 하기에 쓴다)
  .교재기록.jsonl           ← 누가 어디에 썼는지 남기는 작업 기록
```

`index.md`의 「남은 것」에는 완성 시점에 열려 있던 가벼운 지적, 수락한 미확인 사실, 다음 개정 때 할 일이 적힙니다. 한 파일로 읽고 싶으면 세션에서 "합본 만들어줘"라고 하면 됩니다. 최종 검사를 통과한 뒤에만 만들어지며 기본 위치는 `jvm-memory/jvm-memory.md`입니다. 합본은 챕터에서 다시 만드는 파일이라 직접 고치지 않습니다.

### 어떻게 동작하나

#### 지휘자와 다섯 역할

| 역할 | 하는 일 | 쓸 수 있는 곳 |
| --- | --- | --- |
| 메인 세션 (지휘자) | 입력 확정, 일 배정, 단계 통과 판정, 상태 기록, 보고. **본문·계약·리포트는 한 줄도 쓰지 않는다** | 상태 파일, 목차 파일, `미확인-수락.md`, 합본 |
| `curriculum-architect` (설계자) | 목차를 학습 순서·의존성·챕터별 계약(지시서)으로 바꾼다 | `00-설계/` |
| `chapter-writer` (집필자) | 계약 한 장을 본문 한 장으로 쓴다. 지적을 받으면 다시 쓴다 | 맡은 챕터 파일 1개 |
| `technical-reviewer` (정확성 검수) | 사실·코드·계약 위반을 잡는다 | `검수/` |
| `learner-advocate` (독자 검수) | 선수 지식만 가진 독자가 막히는 곳을 잡는다 | `검수/` |
| `learning-editor` (편집자) | 표기를 맞추고 중복을 줄이고 챕터를 잇고 `index.md`를 쓴다. 새 내용은 쓰지 않는다 | 전 챕터(연결·표기만), `index.md` |

검수를 두 명으로 나눈 이유가 있습니다. "맞는 말인가"와 "읽히는가"는 서로 다른 것을 놓치고, 한 사람이 둘 다 보면 판정이 뭉개지기 때문입니다. 동시에 일하는 AI는 최대 3명입니다. 서브에이전트를 띄울 수 없는 세션이면 지휘자가 혼자 역할을 돌려 쓰지 않고, 무엇이 필요한지 알린 뒤 멈춥니다.

#### 지적의 세 등급

검수 지적에는 등급이 붙습니다. **S1(치명)**은 틀리게 배우거나 더 읽지 못하게 되는 결함이라 반드시 고칩니다. **S2**는 오해나 빈틈, **S3**는 걸리지만 막히지는 않는 정도입니다. S2·S3만으로는 진행을 막지 않습니다. 원고의 S3는 엮기 단계에서 다듬고, 끝까지 남은 S2와 계약 탓인 S3는 `index.md` 「남은 것」에 공개합니다. 설계 단계의 S2는 집필 전에 한 번 고쳐 둡니다.

지적마다 원인이 원고에 있는지(→ 집필자) 계약에 있는지(→ 설계자, 이후 설계 검수를 다시 거침)도 적혀 있어, 고칠 사람에게 바로 돌아갑니다.

#### 단계

| 단계 | 하는 일 | 다음으로 넘어가는 조건 |
| --- | --- | --- |
| 0 접수 | 목차·독자·경로·깊이 확정, 작업 폴더 생성 | 접수 검사 통과 |
| 1 설계 | 설계자가 설계서와 챕터 계약을 쓰고, 두 검수자가 **집필 전에** 설계를 검수 | S1 0건 (목차 삭제·범위·순서 변경이 있으면 사용자 확인) |
| 2 집필 | 선수 챕터가 검수를 통과한 장부터, 의존성 순서대로 최대 3장씩 동시에 쓴다 | 자가 점검 |
| 3 검수 | 장마다 정확성·독자 두 검수 | S1 0건 |
| 4 엮기 | 편집자가 한 권으로 다듬고, 바뀐 장은 다시 두 검수 | 최종 검사 통과 |
| 5 인계 | 만든 것·바꾼 것·남은 것을 보고 | — |

2·3단계는 번갈아 돕니다. 앞 챕터들을 쓰고 검수해 통과하면, 그 장을 선수로 둔 다음 챕터들로 넘어갑니다. 전부 쓴 뒤 한꺼번에 검수하지 않습니다. 여기서 「검사」는 아래의 `book.py check`입니다.

#### 믿을 수 있게 만드는 장치

- **판정은 판본에 붙는다.** 판본은 원고의 특정 버전입니다. 검수 리포트에는 검수한 원고의 해시가 적혀서, 원고가 한 글자라도 바뀌면 옛 "통과"는 무효가 되고 다시 검수해야 합니다. 계약이나 앞 챕터가 바뀌어 낡은 원고도 같은 방식으로 잡습니다.
- **확인은 스크립트가 한다.** 지휘자는 단계를 넘기기 전에 `book.py check`로 파일을 직접 검사합니다. 누락된 원고·검수, 남은 S1, 낡은 판정, 깨진 링크, 목차 누락 같은 것이 오류이고, 분량 초과나 S2·S3는 경고만 냅니다. AI의 "다 됐다"가 아니라 이 검사 결과로 다음 단계를 정합니다. 다만 이 순서는 지휘자가 따르는 문서 규칙이고, 별도 엔진이 강제하지는 않습니다.
- **검수 독립성을 깨는 쓰기는 훅이 막는다.** 훅은 역할·스킬 파일 안(frontmatter)에 들어 있어 따로 설정할 필요가 없습니다. 지휘자가 원고·계약·리포트를 직접 고치거나, 검수자가 `검수/` 밖에 쓰거나, 다른 역할이 검수 리포트를 쓰는 Write·Edit를 차단하고, 누가 어디에 썼는지 기록합니다. 보조 장치일 뿐이라 Bash로 쓰는 것은 막지 못하고, 지휘자 쪽 훅은 `/교재`로 시작한 세션에서만 걸립니다.

더 자세한 규칙은 [claude/CLAUDE.md](claude/CLAUDE.md)에서 시작합니다.

## Codex로 사용하기

> 용어 대응: Claude 쪽의 지휘자 = 리더(오케스트레이터), 검수 = 검토, 챕터 계약 = 장별 명세.

저장소 루트에서 시작합니다. 별도의 API 서버가 필요 없고, 링크는 저장소 안(`.codex/`, `.agents/`)에만 만들어 전역 위치는 건드리지 않습니다.

```bash
cd /path/to/ai-harness
bash scripts/install-codex.sh
python3 scripts/doctor.py
codex
```

설치 스크립트는 이 저장소의 역할 디렉터리와 `codex/skills.list`에 등록한 스킬만 상대 심볼릭 링크로 연결합니다. 기존 파일·다른 연결이 있으면 보존하고 오류를 반환합니다. `doctor.py`는 `tomllib`을 쓰므로 Python 3.11 이상이 필요합니다.

Codex 앱에서는 이 저장소를 프로젝트로 열고 **새 세션**을 시작합니다. 프로젝트 설정을 신뢰할지 묻는 경우 본인이 확인한 이 저장소를 신뢰해야 프로젝트 설정이 적용됩니다. 역할을 인식하지 못하면 세션을 다시 시작하고 [Codex 지침](codex/AGENTS.md)의 대체 역할 전달 방법을 확인합니다. 서브에이전트 도구가 없는 실행 환경에서는 이 워크플로를 실행할 수 없습니다.

첫 요청 예시:

```text
아래 목차를 학습서 집필 흐름에 따라 책으로 만들어줘.
메인은 오케스트레이터를 맡고 역할별 서브에이전트를 사용해줘.
독자는 자바 문법을 아는 백엔드 입문자이고, 한국어로 설명해줘.
결과는 books/http-basics/book.md로 만들어줘.

1. HTTP 요청과 응답
2. 메서드와 상태 코드
3. 헤더와 본문
```

목차를 채팅에 붙여 넣거나 [요청 양식](templates/book/request.md)을 복사해 파일로 전달하면 됩니다. 분량·독자·참고 자료는 선택 사항입니다. 목차 삭제·재배열이 필요하거나 주제가 모호하면 관련 선택을 확인합니다.

중단 후에는 `books/<책 이름>`을 지정해 이어서 집필해 달라고 요청합니다. `state.md`와 최신 검토 기록을 바탕으로 재개합니다.

### 책임 분리 (Codex)

| 구분 | 정의하는 것 | 파일 |
| --- | --- | --- |
| 에이전트 | 역할, 산출물 소유권, 판단 기준, 협업 경계 | [codex/agents/](codex/agents/) |
| 스킬 | 배정된 작업의 입력·수행 절차·결과 기준 | [shared/skills/](shared/skills/) |
| 오케스트레이터 | 팀 구성, 작업 배정, 의존성, 단계 전환, 재작업 | [orchestration/](orchestration/) |

| 역할 | 맡는 일 | 스킬 |
| --- | --- | --- |
| 메인 세션 | 작업 조정·기록·사용자 소통 | 집필 스킬을 직접 수행하지 않음 |
| `book_planner` | 목차를 학습 목표와 장별 명세로 설계 | `book-plan` |
| `book_researcher` | 사실·출처·버전 확인 | `book-research` |
| `book_writer` | 배정된 장의 본문·예제·연습·해설 | `book-write` |
| `book_reviewer` | 설계·원고·통합본의 독립 검토 | `book-review` |
| `book_editor` | 검토된 장을 하나의 책으로 편집 | `book-edit` |

역할 파일에는 상세 절차를 넣지 않습니다. 스킬은 작업자 생성이나 단계 전환을 수행하지 않습니다. 리더는 원고를 직접 작성·보완하지 않고 문제를 담당자에게 돌려보냅니다. 저자와 검토자는 서로 다른 작업자이며 역할을 바꿔 겸하지 않습니다.

### 진행 흐름 (Codex)

```text
목차 입력 → 학습 설계 → 설계 검토
                       ↓
           장별 조사 → 집필 → 독립 검토
                       ↓ 모든 장 통과
               통합 편집 → 최종 검토 → book.md 전달
```

서로 독립적인 작업을 최대 3명까지 병렬 실행합니다. 선행 장이 필요한 원고는 그 장의 검토가 끝난 뒤 작성합니다. 자세한 통과 조건과 재작업 규칙은 [집필 흐름](orchestration/learning-book.md)에 있습니다.

오케스트레이션은 메인 Codex가 읽고 따르는 문서 규약입니다. 별도 프로그램이 단계를 강제로 실행하는 워크플로 엔진은 아닙니다. 파일 소유권도 협업 규칙이며 OS 수준의 파일별 접근 제한은 아닙니다. 모델과 권한은 현재 세션 설정을 상속합니다.

### 책의 산출물 (Codex)

```text
books/<책 이름>/
  request.md                   사용자 목차·요구 원문
  state.md                     진행 상태·작업 소유권·재개 정보
  plan.md                      목차 대응·학습 목표·장 의존성
  research/ch01.md             장별 조사 근거
  chapters/ch01.md             장별 원본
  reviews/<작업 ID>.md         독립 판정과 검토 파일 해시
  handoffs/<작업 ID>.md        담당자의 결과·미해결 사항
  book.md                      전체 본문이 들어 있는 최종 책
  README.md                    읽기 안내
```

내용이나 입력 자료가 변경되면 그 자료를 사용한 후행 작업의 검토까지 무효화됩니다. 핵심 사실이 확인되지 않았거나 검토 결함이 남아 있으면 완성본으로 표시하지 않습니다. 산출물은 로컬에 생성되며 커밋·푸시는 별도 요청으로 수행합니다.

## 하네스를 고치는 사람에게

책을 만들기만 한다면 여기부터는 읽지 않아도 됩니다.

### 저장소 구조

```text
CLAUDE.md                      Claude Code 진입점 (claude/CLAUDE.md를 불러온다)
claude/
  CLAUDE.md                    Claude Code 하네스 안내·유지보수 규칙
  agents/*.md                  역할 5개
shared/orchestration/          Claude: 파이프라인·산출물 계약·book.py·hook.py
shared/skills/교재*, 챕터*      Claude: 절차 5개
shared/instructions/교재-공통규약.md   Claude: 문체·형광펜 등 공유 기준

AGENTS.md                      Codex 진입점
.codex/config.toml             Codex: 서브에이전트 활성화·동시 실행 한도
.codex/agents -> ../codex/agents
.agents/skills/book-*          Codex: 등록한 각 shared/skills/book-*로 연결
codex/
  AGENTS.md                    Codex 실행 규칙
  skills.list                  Codex에 연결할 스킬 목록
  agents/*.toml                역할 5개
orchestration/                 Codex: 리더의 책임·작업 의존성과 단계 전환
shared/skills/book-*           Codex: 절차 5개
shared/instructions/book-contract.md, project-guide.md   Codex: 공통 원칙·산출물 계약
templates/book/                Codex: 요청·진행 상태 양식
books/                         Codex: 책별 산출물

scripts/                       설치·정적 점검 (install-claude.sh, install-codex.sh, doctor.py)
tests/                         임시 환경에서 설치·게이트·합본 회귀 검증 (견본 책 포함)
docs/                          하네스 개선 계획·측정 기준선
```

원본은 저장소에서 수정합니다. 설치 스크립트는 원본을 가리키는 링크만 만들고, 링크가 사라지면 다시 실행해 복구합니다. 무엇을 어느 파일에 넣는지는 [claude/CLAUDE.md](claude/CLAUDE.md)의 「하네스를 고칠 때」를 따릅니다.

### 점검

```bash
bash scripts/install-claude.sh --doctor    # Claude 원본 정합성 (설치 전에도 돈다)
python3 scripts/doctor.py                  # Codex 연결·TOML·메타데이터·링크
python3 -m unittest discover -s tests -v   # 두 구현의 설치·게이트 회귀
git diff --check
```

이 점검들은 파일 형식과 연결, 게이트 규칙만 확인합니다. 책의 교육적 품질은 보증하지 않으며, 품질은 책마다 남는 독립 검수 기록으로 확인합니다.

Codex 검색 위치와 파일 형식은 [커스텀 에이전트](https://learn.chatgpt.com/docs/agent-configuration/subagents), [스킬](https://learn.chatgpt.com/docs/build-skills), [AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md) 공식 문서를 기준으로 구성했습니다.
