# 검수자 측정 기준선

`tests/fixtures/`의 견본·결함판·정답표로 검수자를 돌려 적중·누락·오탐을 센 기록이다. 이후 규격·effort·모델을 바꾼 뒤 같은 방식으로 다시 재서 이 표와 비교한다.

## 재는 법

1. `python3 tests/fixtures/baseline.py assemble <판> <스크래치>/<중립 이름>/book`으로 사본을 만든다. 이름에 판 이름을 넣지 않는다
2. 사본마다 검수자 1명을 배정 메시지 형식(산출물 계약 6절)으로 띄운다. 대상은 02장, 입력은 02장 원고·02 계약·설계서·선수 01장·공통규약, 쓸 파일은 `검수/02-<축>.md` 하나다. 작업 공간과 절차·규약·계약 경로 밖은 읽지 않게 한다
3. `python3 tests/fixtures/baseline.py score <판> <리포트>`로 채점한다. 적중·오탐의 정의는 `tests/fixtures/README.md` 「채점」

동시에 3명 이하. 리포트는 파일로만 받는다.

설계 검수(`모드: 설계`인 판)는 사본에 원고가 없고, 배정은 산출물 계약 6절의 설계 검수 형식이다. 대상해시는 `book.py hash <사본>/00-설계`, 쓸 파일은 `검수/설계-<축>.md`다.

### 관찰

- **low 정확성 1회(19)는 코드를 실행하지 않았다.** 도구 호출 4회(읽기·해시)뿐이고 웹도 열지 않은 채 「Java SE API 문서」를 근거로 적었다. 결론(`valueOf`가 `Double.toString`을 거친다)은 맞았지만, 에이전트 파일의 "기억만으로 확인했다고 적지 않는다"를 지키지 않은 회차다. 같은 low의 21은 JDK로 실행했다 — low에서는 검증 여부가 회차마다 갈린다
- medium부터 xhigh까지 정확성 검수자는 모두 JDK로 실행했다. xhigh는 JDK 11·17·21·24 여러 판에서 돌리거나 JDK 소스·버그 트래커까지 봤다. 적중은 같고 비용은 high의 약 1.5배, 시간은 약 2.3배다
- medium~xhigh 사이 오탐 S2(2~3)·S3(5~6) 차이는 2b의 같은 설정 2회 편차(독자 S2 0~3) 안이다. 1회씩이라 셋을 가를 수 없다
- 결정: 두 검수자를 `effort: high`로 고정한다(모델은 `inherit` 유지). low는 검증을 건너뛸 수 있고, xhigh는 적중 차이 없이 비싸다. high는 7의 측정 조건과 같아 이후 비교가 이어진다. 고정하지 않으면 세션 effort가 낮을 때 검수자도 같이 내려간다. 집필자·설계자·편집자는 재지 않았으므로 그대로 둔다
